# PDF日報のローカルOCR

PDFと派生画像は既存の取込保存領域に置きます。通常の取込閲覧権限と原本の3年の保存期限を派生画像にも適用します。期限後はAPIから取得できません。バックアップ・物理削除は既存の保存領域の運用に従います。

## 構成・更新

リポジトリのDocker更新ツールで `app`、`db`、`ocr` を更新します。初回ビルドのみ依存パッケージと公式モデルをダウンロードします。Python依存は `requirements.lock`、モデルは `fetch_models.py` のSHA-256で固定しています。実行時のOCRコンテナは外部接続できない `ocr_internal` ネットワークだけに接続し、原本を外部へ送信しません。

- PP-OCRv5 mobile / PaddleOCR 3.2.0 / PaddlePaddle 3.1.1、CPU 1スレッド、同時実行1。
- MariaDBの排他ロック、永続ジョブ、進捗・試行回数・エラーを利用します。再起動時に実行中ジョブを復旧し、3回失敗後は画面から明示再試行します。保存済みの原読取行は再試行で上書きしません。
- 初期メモリ上限1GB。`OCR_MEMORY_LIMIT` で変更できます。NAS全体のメモリ使用量も確認してください。
- 依存やモデルを戻す場合は旧イメージへ戻します。新規migration 047と保存領域は削除しません。モデル更新は別版として再検証します。

## 操作

「データ取り込み」でPDFを選ぶと、回転の微調整、表の台形補正、罫線を追跡した湾曲補正を行い、補正画像と行境界を保存します。原PDFは保持します。様式設定では保存画像上の緑線を確認し「検出した行を使用」を選びます。「先頭行は見出し」のチェックは帳票に合わせて変更してください。必要なら行境界%を上から順に調整できます。日付・開始・終了の左右を指定し、同じセルに開始〜終了がある様式ではそれぞれの文字部分を指定します。補正画像の行範囲をOCR・行画像・ページ強調で共有します。日付はOCR文字から確認し、行番号から補完しません。

罫線未検出・行数不一致は要確認で初期OFFになります。均等分割へ代替した場合も警告を残します。同じ勤務日の候補が複数ある場合は重複撮影や別作業行を確認してください。既に反映したバッチでは再解析・再試行による保存画像の変更を拒否します。画像座標の仕様が変わった古い様式は補正画像上で設定し直してください。

比較画面は主要4項目を横一列に表示します。「対応先・原読取・理由」を開くと原読取文字、警告、更新理由、明示消去を確認できます。既存行の更新には理由が必要です。右側の手修正はOCR側の再修正より優先されます。

### 補正処理の更新・復旧

新規migration `050_pdf_rectification.sql` は派生画像の補正方法・座標を追加します。既適用migrationや過去の原本を変更しません。問題時は直前のapp/ocrイメージへ戻し、追加列と原PDF・保存画像は保持します。検証は `python ocr/test_geometry.py`（ocrディレクトリからの実行も可）、既存PDF API/UI回帰、日報入力UI回帰で行います。合成帳票で台形・湾曲補正と保存座標上の罫線位置を確認します。

OCRの停止・失敗時は「原本を見て手入力」で続行できます。原本PDFを開き、勤務日・時刻を入力して反映項目を選択します。OCRの解析中も他の日報入力は続けられます。

## 検証記録（2026-09-26）

匿名の活字3行PDFで、画像生成、PP-OCRv5解析、既存値保護、項目選択、二重実行、版競合、確認済みロック、原読取・初回入力元の保持をAPIで検証しました。CPU 1・メモリ上限1GBの外部通信不可コンテナで、解析9.52秒、プロセス最大RSS 523,284KBでした。この測定は開発PC上のDockerです。

手書き帳票の運用受入（項目別精度・修正回数・手入力との総所要時間比較）とQNAP / メモリ2GBのASUSTOR実機測定は別途確認します。実帳票をリポジトリへ入れず、匿名化した対象様式で運用開始前に測定します。低信頼度・不明文字は自動反映しません。
