1. 読み方とシステム全体像

この設計書の目的

Links-Systemは、企業、パートナー、案件、日報、請求、支払、入出金、収支を一つの共有データで扱う運送業務基幹システムです。本書は操作方法だけでなく、入力した情報がどこへつながり、なぜデータを分け、どの時点で変更できなくなるかを確認するための資料です。

初めて使う場合は、実務での使い方と、その理由を読み、各機能章の操作手順・確認例へ進んでください。本書にも、利用順序とその理由、記録に残る作成・変更の経緯を掲載しています。操作画面の画像は「利用マニュアル」、画面内の短い説明は「ヘルプ」、合意済みの正式要件は 仕様MD/ を参照します。

想定する確認手順

  1. 全体フローで対象業務の前後工程を確認する。
  2. 機能別設計から「システムでこの機能を開く」を押し、匿名の検証データで画面を確認する。
  3. 入力、状態、関連機能、主要テーブルを照合する。
  4. 業務乖離チェック表へ、現場での実際の手順、確認者、確認日、対応方針を記録する。
  5. 仕様変更が必要な場合は決定ログへ記録し、IssueとPRで改修する。

対象と前提条件

  • 社内LAN内のPCブラウザから、通常4名程度が同時利用する。
  • 本番はQNAP TS-464、テストはASUSTOR AS3202T、開発はDocker Composeを基本とする。
  • データの共有正本はMariaDBであり、ブラウザ単体のIndexedDBを正本にしない。
  • 企業・パートナー・口座・帳票には機密情報が含まれるため、実データをGit、Issue、設計書、検証資料へ転記しない。
  • 金額計算、承認、確定帳票、入出金予定・実績は、後から経緯を追えることを優先する。

利用者と責務

役割 主な責務 主な制限
管理者 全体設定、ユーザー、確定・取消、障害時の判断 実データを開発資料へ持ち出さない
システム担当者 基盤、取込出力、計算ルール、ヘルプ、画面設定 業務判断を単独で確定しない
総務・事務 マスタ、日報、請求、支払、先払、入出金 確定後のデータを直接上書きしない
営業 担当案件、料金、月次確認、差戻し 担当範囲と権限の範囲で確認する
経営者 精算、入出金、収支の確認 通常入力より確認・判断を中心とする
企業・パートナー 自社・本人に関係する請求、支払、日報の確認 他社・社内管理情報は参照しない

設計上の中心原則

  • ひな形と契約を分ける: 基本案件の後日変更が既存の個別案件を勝手に変えない。
  • 契約と金額を分ける: 単価改定を期間と版で管理し、過去の計算根拠を守る。
  • 実績、承認、帳票を分ける: 日報の入力値、承認時スナップショット、発行済みPDFを同じ可変データにしない。
  • 予定と実績を分ける: 入出金予定を実績で上書きせず、差額・取消・再出力を追跡する。
  • 取消と訂正を履歴化する: 確定済みの値を削除・上書きせず、新しい版、訂正系列、反対取引で扱う。
  • 画面と権限を分離する: メニュー表示だけでなくAPI側でも認証・権限を検査する。

2. アーキテクチャと前提

構成

PCブラウザ
  └─ HTML / CSS / vanilla JavaScript SPA
       └─ HTTPSまたは社内LAN HTTP / Cookieセッション
            └─ Node.js 20 + Express API
                 ├─ MariaDB 10.11（共有データ・セッション・監査履歴）
                 ├─ PDF生成（確定帳票を永続保存）
                 ├─ Excel取込・出力
                 └─ 銀行CSV出力

Docker Compose
  ├─ app コンテナ
  └─ db コンテナまたはNAS上のMariaDB

フロントエンドはReact等のフレームワークを使わない単一SPAです。機能キーを基準にJavaScriptモジュールを遅延読込し、REST APIへアクセスします。APIは起動時に未適用migrationを連番で適用します。

採用理由

  • NASで小規模運用でき、開発PC・テストNAS・本番NASで構成をそろえやすい。
  • ブラウザへ業務データを閉じ込めず、複数利用者が同じ状態を参照できる。
  • ExpressとMariaDBに処理を集約し、権限、計算、確定、トランザクションをクライアント任せにしない。
  • migrationとDockerイメージで、環境差と手作業のDB変更を減らす。

認証と権限

ログイン後のセッションはMariaDBの sessions に保存し、CookieはHttpOnly・SameSite=Laxです。ユーザーは複数ロールを持ち、ロールから機能権限を解決します。機能ごとの既定ロールはコードにあり、管理画面で上書きできます。

画面が非表示でもAPIへ直接アクセスできないよう、ルート側でも認証・機能権限・操作別条件を確認します。本設計書は内部構造を含むため、管理者・システム担当者だけが閲覧できます。

整合性と変更競合

  • 請求・支払・先払など複数テーブルを更新する処理はサーバー側トランザクションで行う。
  • 編集対象は version 等による楽観ロックを使い、別利用者の更新を黙って上書きしない。
  • 既適用migrationは編集せず、新しい連番SQLを追加する。
  • 確定後の帳票・スナップショットは再生成せず、取消・訂正を別記録として残す。

障害・復旧の前提

アプリ更新前に必要なバックアップを取得し、schema_migrations、DB件数、アップロード、PDFの対応を確認します。通常更新でDBボリュームや data/mysql を削除しません。NAS移行・DB置換はリポジトリ管理の専用スクリプトを使い、/api/health が db: "up" を返すまで成功扱いにしません。

採用していない扱い

  • ブラウザローカルDBを共有正本にしない。
  • 発行済み帳票を最新マスタから都度再生成しない。
  • 入出金予定と銀行実績を同じ行の上書きで済ませない。
  • 本番の顧客データをテスト・設計資料・Gitへ複製しない。

機能を分けている理由

似て見える機能 分離理由

マスタ変更の伝播

  • 企業・パートナーの最新表示情報は参照画面へ反映するが、確定帳票の宛先・金額は発行時スナップショットを保持する。
  • 基本案件から個別案件を作るときは必要な契約条件をコピーし、その後は別ライフサイクルとして管理する。
  • 金額データは有効期間と改定系列で解決し、日報日付に適用される版を選ぶ。
  • 計算ルールは下書き、検証、公開を分け、公開済み版を直接書き換えない。

月次締めと確定

事務は現在保存されている日報から請求・支払の下書きを作成できます。営業確認または最終確定では、対象案件の日報承認と下書きの根拠一致を確認します。発行時に帳票番号、明細スナップショット、PDF、入出金予定を作成します。

発行後の変更は元帳票を上書きせず、理由を伴う無効化と訂正下書きを作ります。入出金が実行済みなら、元実績を変更せず差額予定を追加します。

データ層を分離する理由

層 役割 変更ルール
マスタ 企業、パートナー、案件、単価、設定 将来利用する値を変更可能。過去確定値へ遡及させない
実績 日報、提出、先払申請 承認前は権限内で修正。変更履歴・競合を管理

金額と日付

  • 金額は浮動小数ではなくDBの固定小数または整数相当の扱いとし、税・端数規則をサーバー側で統一する。
  • 単価は日報日付と金額データの有効期間から解決する。
  • 管理回の名称、予定日、個別例外日、実行日は別項目として持つ。
  • 出金の休日時調整は前営業日、入金は翌営業日を基本とし、月をまたぐ移動先日付を保存する。

削除・取消・版管理

業務参照されるマスタや取引は原則として論理削除します。公開済み計算ルール、銀行CSV形式、発行済み帳票は上書きせず、新しい版を作ります。取消済みの予定や出力バッチを再利用せず、再作成時は新しい識別子を発行します。

技術一覧の扱い

末尾のDB一覧は、migration適用後の検証DBから information_schema のテーブル、カラム、主キー、外部キー、インデックスだけを取得します。行データ、顧客名、口座番号、帳票内容は取得しません。

9. 実務での使い方と、その理由

この章では、初めてシステムを見る人が「どの画面から始め、何を確認して次へ進むか」を説明します。各機能章の「利用場面と操作手順」「なぜこの手順で利用するか」「利用例と完了の確認」「作成・変更の経緯と根拠」と併せて使います。

最初の読み方・操作の仕方

  1. 自分が確認したい業務を下の利用場面から選びます。
  2. 機能名のリンクで該当章へ進み、前提と手順を読みます。
  3. 章末の「システムでこの機能を開く」で別タブに対象画面を開きます。ログイン後も対象機能へ進めますが、担当ロールで許可された範囲だけを利用できます。
  4. 操作を試す場合は、管理者が用意した検証環境・架空データを使います。設計書の閲覧権限があっても、全業務を操作できるとは限りません。
  5. 実際に表示された状態と本書の完了条件を比較します。相違があれば、対象機能・操作・期待結果・実際の結果を業務乖離チェックへ記録します。

本文中の具体例は説明用です。実在の企業・人物・口座を示しません。ボタンが表示されない場合は、現在の状態・権限・対象選択を確認します。業務要件に将来案として記載された項目が、すべて現行画面にあるとは限りません。

場面1：新しい仕事を始める

  1. 企業マスタで取引先と請求先、パートナーで稼働する人を確認・登録します。
  2. 繰り返す仕事の標準条件を基本案件に登録します。
  3. 個別案件で企業・パートナー・契約期間・支払条件を結び付けます。
  4. 金額データで契約期間に適用する請求・支払単価を確認します。
  5. 基本管理で関連をたどり、日報の対象案件と料金がそろったか確認します。

この順序の理由：相手先が定まり、その相手と行う契約が定まって初めて、日報の対象と計算条件が決まります。基本案件はひな形なので、作成済み個別案件の条件まで自動で同じになるとは考えず確認します。

完了の目安：誰の、どの企業の、どの期間の仕事か説明でき、その日の料金を日報で確認できること。企業や料金だけを登録した状態では、実績入力の準備は完了していません。

場面2：日報を受け取って月の確認を終える

  1. 日報提出で、対象期間の原票を受領した日を記録します。
  2. 日報で実際の勤務・距離・経費を入力して保存します。
  3. 入力者が日ごとの全明細と計算結果を確認し、日次確認を付けます。
  4. 案件×対象月の承認を依頼し、担当者が確認します。差戻しは指摘内容を修正・再確認して再申請します。
  5. 事務作業で未入力・差戻し・承認待ちを確認し、次の処理へ進みます。

この順序の理由：受領は「資料が届いた」、保存は「入力した」、日次確認は「入力者が確認した」、月次承認は「責任者が案件月を確認した」という異なる事実です。どこまで進んだかを分けることで、資料未着や承認待ちを発見できます。

つまずいたとき：対象案件が出ない場合は月・期間・絞り込みを確認します。料金が想定と違う場合は適用日・料金区分・請求と支払の条件を確認します。編集できない場合は日次確認や月次承認の状態を見ます。承認済みのものは権限者による所定の訂正経路を使います。

場面3：請求・支払をまとめ、銀行処理を確認する

  1. 請求・支払で月と対象を選んで下書きを作ります。事前下書きは日報完了前でも準備できます。
  2. 日報から再反映する内容を確認し、追加・控除・手動調整と理由を整えます。
  3. 対象日報の承認と根拠の一致を確認して、営業確認・承認・最終確定へ進みます。
  4. 帳票を発行し、PDFの宛先・番号・明細・合計を確認します。
  5. 入出金管理で、確定から作られた予定の日付・金額・相手先を確認します。
  6. 必要な出金CSVを作成します。銀行での処理・入金結果を確認した後、実績を別に登録します。

この順序の理由：下書きは準備用、確定は金額と根拠を固定する処理、帳票発行は相手に渡す文書を作る処理、実績登録は実際のお金の移動を記録する処理です。PDFやCSVを出しただけでは入出金は完了していません。

先払がある場合：先払いの予定と実行状況を確認してから、正式支払の控除を確認します。分割返済の契約管理を先払で代用しません。

完了の目安：日報→精算明細→発行帳票→入出金予定→実績のつながりを追え、差額・保留があれば理由を説明できること。収支分析で利益を見ても、銀行入出金の確認を済ませたことにはなりません。

場面4：後から間違いが分かった

  • 保存前・下書き：該当画面で修正し、再計算・保存結果を確認します。
  • 日次確認済み：確認を外せる状態なら解除して修正し、再確認します。
  • 月次承認済み・請求支払確定済み：権限者が理由を残し、取消・訂正の手順で根拠から再確認します。
  • 帳票発行済み：発行無効・訂正下書きの経路を使い、元の発行履歴と訂正版を区別します。
  • 入出金実行済み：元実績を残し、差額の予定や返金・訂正を確認します。

この分け方の理由：後工程で既に使われた値を直接書き換えると、どの資料・金額を相手に提示し、何を実際に支払ったか説明できなくなります。変更が及ぶ後工程を確認してから修正します。

場面5：Excelや設定を扱う

  • 旧Excelを登録用の形に整える：マスターデータ取込準備 → 編集用Excelの確認 → DB取込。
  • 現在の業務マスターを一括編集する：DB出力 → Excel編集 → DB取込のプレビュー → 確定。
  • 同梱初期値を調べる：マスターデータ出力 → 現行設定との比較 → 必要な項目だけ復旧。
  • 契約単価を変える：金額データで改定版を作り、適用日前後を確認。
  • 計算式を変える：計算ルール管理で下書き・検証・比較・公開を行う。
  • 操作の説明を直す：ヘルプ編集。詳細な理由・経緯はこの設計書のMarkdownへ追記。
  • 利用者のアクセスを変える：ユーザーのロール・本人範囲と、利用可能メニュー設定を併せて確認。

この使い分けの理由：変換、現行値の編集、初期値の復旧、契約単価、計算式は変更対象が違います。目的と違う機能を使うと、準備しただけなのに登録済みと考えたり、特定契約の変更を全社へ広げたりする原因になります。

現場の業務と比較するための記録例

業務乖離チェックの判定は既定の「一致確認済」「実装済・業務確認待ち」「既知の乖離」「未実装」「対象外」「将来候補」を使います。以下は記入形式の例で、確認実績ではありません。

  • 確認する業務：日報を翌日にまとめて受領記録する。
  • 業務上の期待：操作日ではなく実際の受領日を残せる。
  • 確認操作：日報提出をONにし、提出日を実受領日へ変更する。
  • 現行システム：操作日が初期値。過去の実受領日に変更でき、未来日は不可。
  • 判定：実装済・業務確認待ち。
  • 影響：提出日の誤記で遅延日数と督促対象を誤る。
  • 根拠資料：日報提出一覧仕様、業務要件§3.6。
  • 確認担当・確認日：未記入。実際に操作した担当者が記入する。
  • 対応方針：実受領日の確認を受領登録時の手順に含める。合わなければ差異を具体化して記録する。

経緯の読み方

企業マスタ

目的と設計意図

請求先となる企業の名称、住所、締日、請求送付、担当期間などを一元管理します。表示上の会社情報と、請求・帳票に必要な設定を企業単位で追跡できるようにしています。

利用場面と操作手順

新しい取引先を登録するとき、または請求先・担当者・契約状況が変わったときに使います。

  1. 企業マスタで名称・コードを検索し、既存企業か確認します。終了済みの取引先は終了分も含めて探します。
  2. 新規登録または既存詳細を開き、企業名称・住所・連絡先・締日などを確認して保存します。
  3. 請求先No.0の宛名・送付情報を確認します。部署別など別の請求先が必要なら追加し、使用する案件で選択します。
  4. 基本管理または案件画面で、登録した企業・請求先が選べることを確認します。住所変更後は、次に発行する帳票の宛先も確認します。

なぜこの手順で利用するか

最初に重複を調べるのは、同じ企業の案件や請求が別々の企業IDへ分散することを防ぐためです。企業と請求先を分けることで、同じ会社の複数部署へ請求できます。請求先No.0を確認するのは、新規案件の既定請求先になるためです。

利用例と完了の確認

マスターデータ取込準備

目的と設計意図

受領したExcelを直接DBへ入れず、シートと列を確認できる編集用Excelへ変換し、基盤マスター初期値の復旧を安全に準備します。

利用場面と操作手順

旧Excelをシステムへ移す準備、または基盤設定の選択復旧に使います。画面内の目的を先に選びます。

  1. 原本変換では対象Excelのシート・列・対応先を確認し、編集用マスターExcelを作成します。
  2. 出力Excelの必須値・取込キー・企業と案件等の関連を確認し、登録する内容を整えます。
  3. DBへの登録は「DB取込」でプレビューしてから実行します。変換できただけでは登録完了ではありません。
  4. 基盤設定の復旧では、現行値と初期値のプレビューを確認し、復旧する項目を選んで確定します。採番の次番号など継続性が必要な値は復旧対象として安易に戻しません。

なぜこの手順で利用するか

旧Excelの列構成とDBの項目は同じではありません。変換・人による確認・登録を分けることで、項目の取り違えを登録前に発見できます。初期設定への復旧も、現場で変更した必要な設定まで失わないよう選択して行います。

利用例と完了の確認

旧資料の「得意先」列を企業項目へ対応付けた場合、編集用Excelで名称と取込キー、案件の参照先を確認します。変換段階の完了は編集用Excelの確認、業務DB登録の完了はDB取込結果と登録先画面の照合で判断します。

作成・変更の経緯と根拠

DB取込

目的と設計意図

編集済みExcelを検証し、エラー一覧を確認してからマスターをDBへ登録・更新します。解析と確定を分離し、誤った一括更新を防ぎます。

利用場面と操作手順

所定形式に整えたマスターExcelをDBへ登録・更新するときに使います。

  1. マスターデータ取込準備またはDB出力で作ったExcelを用意します。登録先環境を確認します。
  2. Excelを読み込み、プレビューで追加・更新の対象、参照関係、エラーを確認します。
  3. エラーや意図しない更新があればExcelを修正して、もう一度プレビューします。旧プレビューのまま確定しません。
  4. 内容を確認して登録し、結果件数とエラーを確認します。
  5. 企業・パートナー・案件などの画面で代表レコードと関連を照合します。

なぜこの手順で利用するか

名称だけで同一データと決めると、同名の別人や別契約を上書きする危険があります。取込キーと出力時の版を使って対応を確認し、親データのエラーも確認することで誤った紐付けを防ぎます。Excelから行を消してもDB削除にはなりません。

利用例と完了の確認

企業とその案件を同時に登録するとき、企業行がエラーなら案件側の関連も確認します。「ファイル読込成功」で終わらせず、確定結果の件数と、案件画面で正しい企業を参照していることを確認します。過去料金版の訂正はExcel再取込ではなく金額データの訂正経路を使います。

前提・入力・処理・出力

所定形式のExcelを入力し、列、型、必須、参照先、重複を検査します。プレビュー、エラーExcel、確定結果を出力します。

DB出力

目的と設計意図

現行DBのマスター値を、人が確認・編集できるExcelへ出力します。DBダンプではなく、再取込可能な業務マスター形式を対象にします。

利用場面と操作手順

  1. 対象環境と出力対象を確認し、DB出力から編集用Excelを取得します。
  2. 変更が必要な項目を編集します。取込キーや関連を表す項目を不用意に変更しません。
  3. 反映する場合はDB取込で差分・エラーを確認してから確定します。
  4. 登録先画面を再表示し、変更した項目と関連先を確認します。

なぜこの手順で利用するか

現行値を元に編集することで古いExcelによる上書きを減らします。出力後に別の人が更新する可能性があるため、再取込時にも版と変更対象の確認が必要です。業務マスター用Excelは、帳票・添付・DB全体を復元するバックアップとは用途が異なります。

検証用データ

目的と設計意図

匿名のマスター・日報・承認・精算・出力を段階生成し、実データを使わず業務フローを検証します。専用環境・専用DBでのみ利用する安全機能です。

利用場面と操作手順

業務の受入確認、操作練習、計算や帳票の確認用に、専用検証DBでデータを作ります。

  1. 検証用の接続先・環境であることを確認し、件数・期間・通常勤務や例外などのケースを設定します。
  2. サンプルをプレビューし、対象期間や金額・稼働条件を確認して設定版を承認します。
  3. 日報、提出・月次承認、先払・請求・支払、確定・帳票・入出金の順に、前段ジョブの完了を確認して生成します。
  4. 各段階の検証結果を確認し、失敗時はジョブの状況を確認して再開します。
  5. 生成した案件を業務画面で開き、確認したい操作と期待結果を照合します。

なぜこの手順で利用するか

段階を分けることで、料金計算の問題か、月次承認・精算・出力の問題かを切り分けられます。設定版を承認してから生成するのは、確認した条件と実際の生成条件を一致させるためです。生成完了は業務要件への一致確認そのものではありません。

利用例と完了の確認

完了月・前月・当月を用意して、承認済み・差戻し・入力途中の案件をそれぞれ確認します。件数だけでなく、未来日の実績がないこと、不要日の扱い、請求・支払・帳票の根拠一致を確認します。検証専用銀行CSVを銀行へ送信しません。

計算ルール管理

目的と設計意図

日報から請求・支払金額を導く計算式と優先順位を版として管理します。編集、検証、比較、公開を分け、公開済み計算を黙って変更しません。

利用場面と操作手順

契約単価の変更ではなく、計算の式・適用条件・処理順序を保守するときに使います。

  1. 変更する業務規則を仕様と決定ログで確認し、公開中の版から下書きを用意します。
  2. 対象の規則・条件・式を編集し、構文と必須処理の検証を実行します。
  3. 旧版との比較と、通常・休日・不足・控除など対象ケースの期待値を確認します。
  4. 合意した結果を確認して公開します。再計算が必要なら、未確定下書きの対象を確認して選択再計算します。
  5. 再計算結果と最終確定時の結果を照合します。

丸め処理を見直す場合、端数が出る匿名ケースを旧版と新版で比較します。差が意図したケースだけに出るか、請求と支払の両側を確認します。画面の標準例比較は全実データの検証ではないため、対象案件に近いケースも確認します。

日報

追加項目は /api/additional-items に日別または期間別で複数保存します。直接金額・単価数量・自家用燃料費を選び、請求/支払を独立して保持します。燃料は適用日付きの全社/パートナー/案件設定と価格履歴から日額切上げを合計し、日別根拠を保存します。月次承認時に固定し、精算明細と収支分析へ接続します。税込区分は内税を分離し、外税を二重加算しません。確認/承認/精算中の変更は拒否し、既存設定変更で過去額を再計算しません。

PDF取込は /api/daily-report-imports/pdf で受け付け、独立したCPUワーカーが永続ジョブを処理します。実際の原本行画像・原読取値・修正値・現在値を比較し、期待する日報版と反映項目を指定して保存します。原読取と初回入力元は変更しません。空欄は削除扱いにせず、確認・月次承認・精算済みは保護します。様式設定、手入力継続、失敗再試行を提供します。構成と検証限界は ocr/README.md に記載しています。

目的と設計意図

案件ごとの勤務実績、時刻、距離、経費、休暇等を日単位で記録し、請求・支払計算の根拠にします。入力値、計算結果、承認スナップショットを分離して追跡します。

利用場面と操作手順

日々の勤務実績を入力し、月次の承認と請求・支払の根拠をそろえるために使います。

  1. 対象月と個別案件を選び、企業・パートナー・締日が合っているか確認します。
  2. 日ごとに開始・終了、合計休憩、距離、経費、必要な作業明細を入力します。翌朝までの勤務は勤務日基準で、例えば20時から翌4時を 20:00～28:00 と表します。
  3. 自動選択された料金区分と請求・支払それぞれの計算結果を確認します。例外は理由を残して、画面で用意された調整操作を使います。
  4. 保存後、その日の全明細を確認して日次確認を付けます。月の入力と確認を終えたら案件×月の承認を依頼します。
  5. 差戻しがあれば指摘箇所を修正・再確認して再申請します。日次確認済みの計算項目を直す場合は確認を外します。月次承認済みの場合は所定の取消・訂正手順へ進みます。

なぜこの手順で利用するか

時刻・距離は事実、料金・丸めは契約条件、承認は確認責任という役割が異なります。入力後に計算を確認するのは、同じ勤務でも請求側と支払側の条件が異なるためです。日次確認は入力者の確認であり、月次承認とは別です。後工程がどの版を根拠にしたか追えるよう、確認と承認の時点で記録を残します。

利用例と完了の確認

架空の案件で 09:00～18:00、休憩 1:00 を入力した場合、実働が8時間になることをまず確認します。請求・支払額はその案件の契約条件と照合します。入力件数だけで完了と判断せず、日次確認、月次承認、請求・支払への反映を順に確認します。未確認日が残る場合の警告は内容を確認して判断し、未確認を黙って完了扱いにしません。

主要API・データ

日報提出

目的と設計意図

FAX、紙、メール等で日報を受領した事実を、案件と月3回の確認単位で管理します。勤務実績の入力件数だけで「受領済み」と判断しないため、日報本体と分けています。

利用場面と操作手順

FAX・メール・紙などの日報が届いたか、誰に提出を依頼する必要があるかを確認します。

  1. 対象月を選び、パートナーと案件、3サイクルの対象期間を確認します。
  2. 対象期間の日報を受領したら提出状態をONにし、実際の提出日を確認します。初期値は操作日なので、別日に届いていた場合は修正します。
  3. 未提出と遅延日数を確認し、必要な相手先へ確認します。遅延日数を手修正する場合は根拠を業務確認記録へ残します。
  4. 受領資料を日報入力と照合し、事務作業で入力・承認の進捗も確認します。

なぜこの手順で利用するか

資料が届くことと、システムへ入力されることは別の出来事です。入力済みだから受領済みと自動判定すると、代理入力した案件の原票が未着でも見落とします。3サイクルで確認することで月途中の未提出も把握できます。

利用例と完了の確認

10日分までの資料を12日に受領して13日に記録する場合、提出日を12日に直します。受領の記録後も日報が未入力なら入力作業は残ります。対象期間と提出日が原票の受領事実と一致し、未提出が追跡できればこの画面の確認は完了です。

作成・変更の経緯と根拠

2026-09-06確定の受領管理では、入力済み日報から自動判定せず、パートナー未割当てを含む個別案件を対象にすることが決まりました。基本提出日は期間最終日＋1暦日で、全社猶予日を加えて期限を判定します。参照: 仕様MD/09_日報・精算・帳票_業務要件.md §3.6。

状態・制御・注意点

先払い

目的と設計意図

月途中に行う前払を、5・10日、15・20日、25日・末日の3サイクルで管理し、最終支払控除と入出金予定へつなげます。分割返済とは別の業務概念です。

利用場面と操作手順

月次精算前に支払の一部を先に渡す案件について、各サイクルの金額と予定を確認します。

  1. 対象月を選び、個別案件の支払区分が「分割」になっている対象案件を確認します。
  2. 3サイクルそれぞれの対象期間、確認済み日報の稼働日数、分割単価、元金額、手数料を確認します。
  3. 当月の対象外サイクルはOFFにします。金額・手数料を元値から変更する場合は理由を入力します。
  4. 対象を選んで予定を作成し、入出金管理の当月20日回、末日回、翌月10日回への反映を確認します。
  5. 振込後は入出金実績を記録し、正式支払時に実行済み先払の控除を確認します。

なぜこの手順で利用するか

予定を作っただけで先払済みとすると、実際には振り込んでいない額を正式支払から差し引く原因になります。対象期間・予定・実行を分けて照合するのは二重支払や二重控除を防ぐためです。「分割」という案件区分は、物品立替等の分割返済契約とは別の意味で使われます。

利用例と完了の確認

5日・10日締めサイクルの先払を作るときは当月20日回へつながることを確認します。稼働0日の案件も一覧に出ますが、予定作成対象はONかつ1円以上のセルです。未実行の誤りは理由付き作成取消、実行済みの誤りは返金・訂正予定で対応し、元実績は残します。

作成・変更の経緯と根拠

主要API・データ

状態・制御・注意点

未実行予定の取消と実行済み訂正を分けます。取消済み予定を再利用せず、金額変更理由と楽観ロックを必須とします。

支払

目的と設計意図

パートナーへ支払う原価を日報から下書きし、先払・会費等の控除、手動調整、確認、確定、支払明細発行、出金予定作成まで管理します。

利用場面と操作手順

パートナーへの月次支払を計算し、先払や手数料等を差し引いた最終振込額を確認します。

  1. 対象月、パートナー、対象案件を確認して支払下書きを作ります。
  2. 日報からの自動明細と必要な調整を確認し、支払総額の根拠を照合します。
  3. 実行済み先払、手数料、その他控除について、対象・金額・理由を確認します。先払予定だけを支払済みとみなしません。
  4. 日報承認と明細の一致を確認し、営業確認・承認・最終確定・帳票発行へ進みます。
  5. 支払明細の振込額と入出金管理の出金予定を確認し、銀行処理後に実績を記録します。

なぜこの手順で利用するか

日報の支払合計は控除前の金額であり、銀行へ振り込む額とは限りません。総額、先払、控除、振込額を分けて確認することで、先に支払った額を二重に払うことや、同じ控除を二度差し引くことを防ぎます。

利用例と完了の確認

説明用に支払総額100,000円、実行済み先払20,000円、その他控除1,000円、他の調整なしなら、差引は79,000円です。これは税等を省いた控除の読み方の例です。実際の帳票では全控除と税区分を確認し、出金予定・実績まで一致するか照合します。

作成・変更の経緯と根拠

仕様MD/09_日報・精算・帳票_業務要件.mdは、先払と立替金の分割返済の混同を防ぐために業務の境界を整理しています。2026-09-09の決定ログでは日報・請求・支払を案件月単位で確認する流れが定められました。分割返済専用管理の未確定部分を、先払機能で代用することは想定していません。

利用者・権限

管理者、総務、営業、経営者、パートナーユーザーが役割に応じて利用します。確定・取消は限定ロールです。

前提・入力・処理・出力

対象月、パートナー、案件、日報を選び、支給・控除明細を編集します。確認・確定後に支払明細PDFと出金予定を出力します。

関連機能・前後工程

承認済み日報、支払料金、先払、控除規則を参照し、入出金管理と収支分析へ連携します。

主要API・データ

支払ヘッダー・明細・日報対応、共通精算明細・根拠・文書・ワークフロー、控除規則を保持します。

状態・制御・注意点

支給と控除の計算順、税区分、最終振込額をサーバー側で統一します。確定後は直接編集せず無効化・訂正系列を使います。

現行業務との乖離・確認事項

会費、G会費、保険、手数料、控除不能時、分割返済の正式規則は継続確認が必要です。

今後の改善

パートナー向け承認閲覧、控除根拠の説明、不能額の繰越、銀行実績照合を検討します。

入出金管理・FB出力

目的と設計意図

月6回の管理回に入出金予定を集め、実績、口座調整、銀行CSVの版と履歴を管理します。管理回、予定日、実行日、予定、実績を分離します。

利用場面と操作手順

「いつ・誰から／誰へ・いくら入出金する予定か」と、実際の結果を確認します。

  1. 対象月と画面上の「締日」（内部の管理回）を選び、請求・支払・先払から連携した予定を確認します。
  2. カレンダーの日付を1回クリックすると当日の概要、ダブルクリックすると当日一覧へ進めます。個別予定日と入金／出金の方向を確認します。
  3. 出金CSVが必要な場合は振込元口座と公開済み形式を選び、対象、口座不備、件数、合計を確認して出力します。
  4. 銀行での処理結果を確認した後、実行日・実行額を実績登録します。未処理や保留はその状態で残します。
  5. 予定と実績の差を確認します。銀行預金表示は別の口座調整台帳を使うため、必要な調整は「口座調整」で確認します。

なぜこの手順で利用するか

締日別の管理単位と、銀行で実際に動いた日は一致するとは限りません。CSVの作成も銀行の処理成功を意味しません。予定・出力・実績を別々に確認することで、出力しただけの支払を実行済みにする誤りを防ぎます。口座残高の表示に実績が自動加算されると考えないことも重要です。

利用例と完了の確認

10日回の支払予定日が休日調整で前営業日になっても、管理上の所属は10日回のままです。CSV出力後に銀行で保留となった場合は実行済みにしません。完了は予定額・銀行結果・登録実績を照合して判断します。正式な銀行形式が未確認のCSVは銀行提出用として利用できません。

作成・変更の経緯と根拠

仕様MD/10_入出金管理・FB_業務要件.mdは、旧Excelの月6枚のシートを6つの管理回へ置き換えた経緯を明記しています。2026-09-06の決定では銀行CSVの版管理、出力と実行の分離、出金は前営業日・入金は翌営業日への調整が定められました。銀行明細自動照合と正式FBの未確定部分は後続課題です。

利用者・権限

管理者、総務、経営者が利用します。銀行形式・口座設定は管理権限を持つ担当者に限定します。

前提・入力・処理・出力

請求・支払・先払から予定を受け、手動予定、個別日付、実績、口座調整を入力します。振込元口座と公開済み銀行形式を選んでCSVを生成します。

関連機能・前後工程

請求の入金予定、支払・先払の出金予定を受け、実績・出力履歴を保持します。分析や将来の消込の基盤になります。

主要API・データ

管理回、予定、実績、CSVバッチ・明細、振込元口座、口座調整台帳、銀行形式・版・列定義を分離します。

状態・制御・注意点

CSV生成は振込実行ではありません。不備行を黙って除外せず、公開済み形式を上書きせず、実行済み明細を含む出力取消を禁止します。

現行業務との乖離・確認事項

正式FB列、承認分離、実績照合は未確定です。表示残高は期首残高と手動調整であり、取引実績を自動反映しません。

今後の改善

契約銀行の正式FB、銀行明細取込、自動消込、口座残高自動反映、承認ワークフローを検討します。

収支分析

目的と設計意図

日報・請求・支払の結果を、収支一覧、企業別利益率、稼働日の3つの見方で確認します。分析結果を取引正本として編集せず、根拠データへ戻れる参照機能とします。

利用場面と操作手順

月の収支、企業ごとの利益率、パートナーの稼働状況を確認し、原因を調べるために使います。

  1. 対象月と企業・パートナー等の条件をそろえます。
  2. 収支一覧で売上・原価・利益を確認し、企業別利益率、稼働日の表へ切り替えて偏りを確認します。
  3. 予想と異なる値があれば、同じ対象月・案件の日報、請求、支払へ戻って確認します。
  4. 修正が必要なら元の業務画面で適切な訂正を行い、分析を再表示して結果を確認します。

なぜこの手順で利用するか

利益が下がった理由は、単価だけでなく稼働日数、入力漏れ、控除、締め状況など複数あります。同じ対象範囲で3表を比較し、元データへ戻ることで、集計値を直接書き換えずに原因を直せます。収支と銀行残高は異なる指標です。

利用例と完了の確認

架空の企業Aの利益率が低い場合、企業別利益率だけで判断せず、収支一覧の対象案件と稼働日を確認します。請求・支払が下書きか確定済みかも元画面で確認し、どの時点の数字を比較したかを記録します。Excelとの照合では対象月、対象案件、除外条件をそろえます。

ヘルプ編集設定

目的と設計意図

各画面ヘッダーの「ヘルプ」に表示する短い概要と、入力・操作の影響説明を編集します。全体教育を行う利用マニュアルや内部設計書とは役割を分けます。

利用場面と操作手順

利用者がその画面で迷う項目や操作について、短い説明を追加・修正します。

  1. 対象の画面キーを選び、現在表示されるヘルプを確認します。
  2. 概要と「何を入力すると、どうなるか」を、実際の項目名に合わせて編集します。
  3. 保存後に対象画面の「ヘルプ」を開き、本文と表示を確認します。
  4. 業務の前後関係は利用マニュアル、理由・経緯は本設計書にも反映します。

なぜこの手順で利用するか

操作中には、その場で必要な短い説明が役立ちます。説明だけ先に変えると実装と食い違うため、対象画面の挙動を確認して記載します。ヘルプの保存は業務条件や計算処理を変える操作ではありません。

利用例と完了の確認

日報の確認チェックについて「入力者の日次確認で、月次承認とは別」と追記します。対象画面でその説明が読め、実際の操作と一致していれば完了です。ヘルプ本文の更新番号と、稼働システムのビルド識別子は別物です。

作成・変更の経緯と根拠

2026-09-09の決定ログで、管理者・システム担当者が画面概要と操作影響を変更する専用機能が定められました。初期計画の「画面定数でDB化しない」という記述は、後の決定と現行の help_contents 保存方式に置き換わっています。2026-09-12、Issue #140ではシステム版情報を本文から独立させました。

利用者・権限

管理者とシステム担当者が編集し、保存した説明は該当画面を利用できる全利用者が参照します。

前提・入力・処理・出力

画面キー、タイトル、概要、操作説明を入力し、画面別ヘルプモーダルへ出力します。

関連機能・前後工程

機能追加時に画面キーとヘルプを追加し、利用マニュアル・設計書の詳細へ必要に応じて誘導します。

主要API・データ

help_contents に画面キーごとの本文、版、更新日時を保存します。

状態・制御・注意点

ヘルプへパスワード、個人情報、口座情報、実データを記載しません。業務仕様をヘルプ編集だけで変更しません。

現行業務との乖離・確認事項

利用者がつまずく箇所と説明量が適切か、画面受入時に確認します。

今後の改善

利用可能メニュー選択

目的と設計意図

役割ごとに利用できる機能を設定し、組織変更に対応します。コード上の安全な既定値を持ちつつ、DBの設定で上書きします。

利用場面と操作手順

組織の役割に合わせ、どのロールがどの機能を使えるかを変更します。

  1. ユーザー管理で実際の担当者に付いているロールを確認します。
  2. 利用可能メニュー選択で、対象ロールと機能の許可を変更して保存します。
  3. 対象ロールの確認用アカウントで再表示し、メニューと対象機能のアクセスを確認します。
  4. 承認・確定・取消など、機能内の操作権限も別に確認します。

なぜこの手順で利用するか

この設定は人の名前ではなくロールに適用されます。兼務で複数ロールを持つ人もいるため、チェック表だけでは実際の利用範囲を判断できません。メニューの許可と重要操作の許可は別の制限も持つので、画面が開けるだけで承認権限があるとは限りません。

利用例と完了の確認

ある担当グループへ新機能を許可する場合、利用者のロールと保存後の実際のアクセスを照合します。管理権限を持つ経路が残ることも確認します。設計書の閲覧は管理者・システム担当者限定で、このメニュー表だけでは一般利用者へ開放できません。

前提・入力・処理・出力

機能とロールの許可行列を入力し、版競合を検査して保存します。次の操作から各利用者の権限へ反映します。

関連機能・前後工程

主要API・データ

状態・制御・注意点

メニュー非表示だけを安全対策にせずAPIでも検査します。検証用データ等は権限があっても環境制約を維持します。

現行業務との乖離・確認事項

役職名と実際の操作責任が一致するか、承認・取消等の操作別制限と併せて確認します。

今後の改善

UIビルダー

目的と設計意図

一覧画面の表示列、順序、幅等を利用目的に合わせて調整します。業務データや権限そのものを変更せず、見え方だけを管理します。

利用場面と操作手順

主一覧で必要な情報を見つけやすくするため、表示列や順序を調整します。

  1. UIビルダーで対象の主一覧を選び、現在の列構成を確認します。
  2. 業務上必要な列を表示し、比較しやすい順序・幅へ調整して保存します。
  3. 対象一覧を開き直し、状態、名称、必要な操作が確認できるか点検します。
  4. 共通設定が他の利用者にも適切か、狭い画面で読めるかを確認します。

なぜこの手順で利用するか

表示列を共通化すると、担当者同士が同じ情報を見て確認できます。列を隠すことはデータの削除や参照権限の制限ではありません。表示内容の整理と権限の設定を混同しないように使います。

利用例と完了の確認

企業一覧で締日を見つけやすくしたい場合、締日の表示・順序を調整して一覧で確認します。先払マトリクス、日報月次グリッド、入出金カレンダーなどは、この主一覧の列設定とは対象が異なります。画面種別を確認してから変更します。

前提・入力・処理・出力

ユーザー管理

目的と設計意図

ログインID、表示名、複数ロール、所属、担当範囲、企業・パートナー本人紐付け、有効状態を管理します。本人情報と機能権限を分けて扱います。

利用場面と操作手順

新しい担当者への利用開始、異動・兼務の変更、利用停止時に使います。

  1. ログインIDの重複を確認し、表示名と担当業務に必要なロールを設定します。
  2. 所属・担当範囲を確認します。企業・パートナー用アカウントでは本人に対応する企業・パートナーとの紐付けを確認します。
  3. 保存後、対象アカウントでログインし、必要な機能と対象範囲が表示されるか確認します。
  4. 異動・退職時はロールや有効状態を見直し、業務履歴に残る担当者を追跡できる状態を保ちます。

なぜこの手順で利用するか

ロールは利用できる機能、本人紐付けや担当範囲は参照する業務データを決めます。片方だけ設定しても適切な利用範囲にはなりません。個人単位のアカウントを使うことで、承認・訂正・設定変更を誰が行ったか確認できます。

利用例と完了の確認

検証パートナーAの確認用アカウントなら、パートナーロールに加えてAの本人紐付けを設定します。ログイン後にAの対象が見え、権限外の相手先へアクセスできないか確認します。管理者アカウントだけで確認を終えないようにします。

利用者・権限

管理者とシステム担当者が管理します。利用者は自分に付与された範囲だけを利用します。

前提・入力・処理・出力

ID、パスワード、表示名、ロール、部署、エリア、本人紐付けを入力します。認証後に公開用ユーザー情報と機能権限をセッションへ出力します。

関連機能・前後工程

利用可能メニュー設定がロールから機能権限を決めます。承認、取消、監査ログはユーザーIDを記録します。

主要API・データ

状態・制御・注意点

無効ユーザーはログインできません。パスワードを平文保存・表示せず、最後の管理者を失わないようにします。削除は原則無効化です。

現行業務との乖離・確認事項

兼務、代理入力、退職・異動、企業・パートナー本人の閲覧範囲が実運用と一致するか確認します。

今後の改善
