# 検証データ作成ツール：初回納品

## 実装済みと未実装

実装済み: 管理者向け取込、名称の維持/仮想化、コード列割当、件数・期間・勤務割合、サンプル、採否・コメント保存、版承認、匿名JSON/CSV、完成Excelから登録済みのマスターを日報サンプル設定へ連携、承認済み設定から専用検証DBへの日報生成、3サイクルの日報提出と月次承認生成、承認済み月次データからの先払・請求・支払生成、請求・支払の最終確定、先払控除、確定帳票PDF、入出金予定・実績・手動予定、検証専用銀行CSV。

未実装: 料金・契約期間列の取込、コードの関連付き仮想化、任意勤務帯、契約/料金改定、正式FB、分析、生成DB移送・復元。正式FBは現行システム自体が未対応のため、検証専用銀行CSVを正式FBとして扱わない。
画面上の日報サンプルは金額未計算の設計値である。承認後に日報生成ジョブを開始すると、登録済みマスターを再照合して現行料金計算を実行し、100件単位で専用検証DBへ保存する。同じ設定版は同じジョブを再利用し、失敗後は生成済み対応表を使って続きから再開する。企業・パートナー・基本案件・個別案件の有効期間外は勤務不要へ補正し、稼働日の請求・支払が0円なら生成完了にしない。
担当者カタログは作成するが、企業への営業配属・分析は後続。過去の固定生成スクリプトは呼び出さない。

## 独立環境の起動（Windows / NAS 共通）

通常の `docker-compose.yml` と重ねない。新規の専用Compose・専用DB・専用ボリュームを使用する。
Git管理外の `tmp/test-tool.env` に以下の変数を設定する（値は各環境で生成した別々の秘密値）。

- TEST_TOOL_ROOT_PASSWORD
- TEST_TOOL_DB_PASSWORD
- TEST_TOOL_SESSION_SECRET
- TEST_TOOL_ADMIN_PASSWORD

Windowsでは、リポジトリ直下から専用ラッパーを実行する。内部で共通の `docker-update.ps1` を呼び、専用Composeだけを選択して起動・health確認する。

```powershell
pwsh -NoProfile -File scripts/test-data-update.ps1
```

DockerコマンドがPATHにない場合はDocker Desktopの `resources/bin` をプロセスのPATHへ追加して実行する。ラッパーは既存8080番と混同しないよう localhost:8088 に固定する。
NAS SSHでは同じ共通更新ツールへ専用Composeと環境ファイルを指定する（NASへ導入する場合だけ実行）。

```sh
COMPOSE_FILE=docker-compose.test-data.yml COMPOSE_ENV_FILES=tmp/test-tool.env COMPOSE_PROJECT_NAME=links-test-data-tool bash scripts/docker-update.sh --health-url http://127.0.0.1:8088/api/health
```

`http://localhost:8088/api/health` が `db: "up"` であることを確認し、`test-admin` でログインする。
設定メニューの「検証データ作成」を開く。NASも既定はlocalhostのみで公開する。
NASへは `ssh -L 8088:127.0.0.1:8088 NASユーザー@NASホスト` でトンネル接続し、PCのlocalhost:8088から利用できる。
NASへ外部公開する設定や既存DBの接続情報を流用しない。通常業務のユーザー・データはこの環境へ持ち込まない。

停止は同じCompose指定で `stop`。復旧は最後に確認したコードへ戻して同じ専用環境を起動する。
通常のDB・`data/mysql`・既存ボリュームを削除しない。専用DB内の設定を保持するため `down -v` は使用しない。
生成DBの移送/復元は後続実装のため、初回は匿名共有JSON/CSVのみを移送する。

## 操作

1. xlsx/csvを選び、文字コード・シート・列割当を確認する。ファイルなしなら仮想データを使う。
2. コードは文字列として用意する。Excelの表示書式だけで付けたゼロは復元できないため、文字列の値にして渡す。
3. 左側の日本語項目と右側のExcel列を順にクリックして連携する（逆順でも可）。右側は列名・先頭2行の見本を表示する。×で解除でき、シート選択で切り替えても連携は残る。名称以外の仮想化は明示的に拒否する。
   企業の担当・形態・検索用・企業番号などを保持可能。担当・形態は元値の保存であり、担当者マスターや形態コードの作成ではない。
   シート名と列名から取込先を初期判定する。画面上部の「このシートの扱い」は、そのシートを取り込むか除外するかの指定である。
   同じシートで取込先を切り替えても既存の連携は消えず、企業・パートナー等をまとめて設定できる。上部の取込先チップで設定済みマスターを確認・再表示する。
   同じ番号の行は、エラー・先の行優先・後の行優先・数値平均の切捨て／切上げを取込先ごとに選ぶ。平均対象は締日・分割単価・契約単価・委託単価で、口座番号等は数値として平均しない。
   「設定を保存してサンプル表示」を押すと未反映の列連携も自動反映する。「列の連携を設定へ反映」で先に反映することもできる。同じExcelを再選択すると保存した対応付けを復元できる。
4. 件数は取込を優先する。「マスターデータ取込」で完成Excelを登録済みなら「登録済みマスターを利用」で企業・パートナー・基本案件・個別案件を引き継げる。複数案件に配属された人物は、同日の稼働案件を交替させて勤務重複を防ぐ。契約期間のサンプル反映は未対応。
5. プリセット・必須ケース・割合を3列のケースカードで設定し、サンプル表示する。「サンプルに必ず1件以上含める」は該当パターンを最低1件作る指定。「不足する名称・関連先を仮の値で補うことを許可する」は、表示された仮想補完を承認する指定である。
6. 要調整がなく必須ケースを満たす版だけ承認する。変更後は保存・再表示・再承認が必要。
7. 匿名共有内容を確認し、JSONまたはCSVを保存する。自由コメント・維持値は含まれない。匿名版は再サンプリングされ、元の勤務配置そのものではない。
8. 承認済み版で「承認済みサンプルから日報を生成」を押す。完了月は日次確認済み、処理中月は確認済みと下書きの混在、当月は下書きとして登録される。画面の件数と検証結果を確認する。
9. 日報生成の完了後に「日報提出・月次承認を生成」を押す。各案件月へ締日別3サイクルの提出状況を作り、完了月は原則承認済み、前月は承認済み・承認待ち・差戻し・未申請、当月は提出途中とする。前月は5名を意図した提出遅延として残す。基準日後の提出・承認は作らない。
10. 月次生成の完了後に「先払・請求・支払を生成」を押す。承認済み案件月だけから精算明細を作り、完了月は承認済み、前月は下書き・営業確認依頼・営業確認済みを混在させる。先払は異なる30名へ3サイクルずつ作り、実行済み・保留・取消と理由付き金額変更を含める。請求・支払には各6件の手入力調整を含める。実行済み先払は支払確定時の控除候補になるが、この段階では支払を最終確定せず、PDF・通常支払予定・銀行CSVも作成しない。
11. 精算生成の完了後に「確定・帳票・入出金を生成」を押す。承認済み精算だけを既存の最終確定処理へ渡し、先払控除、確定PDF、入出金予定・一部実績、手動予定6件を作る。振込先の不足値は専用検証DBだけで仮想補完する。検証用の3プロファイルと3振込元口座を作成し、出金予定がある管理回から銀行CSVを生成する。CSV出力済みと入出金実行済みは別状態で保持し、正式FBや銀行送信には使用しない。

取込案件の締日が空欄または不正な場合、専用検証DBに限り `5`、`10`、`15`、`20`、`25`、`end` を一定順で補完し、元値と生成値を追跡テーブルへ保存する。既存の月次承認がある案件月は削除・上書きせず、生成マニフェストの `preservedExistingApprovals` に記録する。

原本はメモリ解析のみ。維持を選んだ値は設定JSONとして専用DBに保存される。
各ファイル2MB、合計10MB、xlsx展開後20MB、10シート、各種類500件・40列、最大50,000案件日。
数式セル・マクロ・外部参照は禁止。値だけのxlsx/csvを使用する。

## テスト

backendで `npm ci` 後、以下を実行する。

```sh
node --test test/test_data_tool.test.js test/test_data_api.test.js
node test-e2e/test_data_ui.js
```

ブラウザはPlaywrightのChromiumを使用する。インストール済みChromeを使用する場合は `BROWSER_CHANNEL=chrome` を環境変数に設定する。
APIテストは管理テーブルのテストダブルを使用し、既存DBには接続しない。
実DB受入テストは専用コンテナ内で `node test-e2e/test_data_live_ui.js` を実行する。専用DB名・環境フラグを検証し、実際のログインから設定保存・承認・匿名出力まで確認する。管理テーブルに確認用の設定を1件保存するが、業務テーブルの件数不変を検査する。
