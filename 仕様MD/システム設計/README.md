# 現行システム設計書の編集ガイド

このフォルダのMarkdownが、Links-System現行システム設計書の正本です。生成済みHTMLの `システム設計書/` は直接編集しません。

## 読み手と目的

- 初めてシステムを確認する業務担当者: 画面を操作しながら、前後工程と設計理由、現行業務との差を確認する。
- 管理者・システム担当者: 権限、API、DB、運用制約、将来改善の影響範囲を確認する。
- 開発者・AI: 機能追加時に、仕様・コード・設計書の記載漏れを防ぐ。

HTML版は稼働中のシステムの `/system-design/` で開きます。管理者またはシステム担当者のログインが必要です。

## 更新方法

HTMLの各章上部にある「○○の原稿（Markdown）を開く」から、対応する原稿を日本語の章名で探せます。原稿ページには閲覧用本文、正本のパス、Markdownのダウンロードを掲載します。

元ファイルを編集するときは、初回にPCの `LinksSystem` フォルダーの絶対パスと編集ソフト（VS Code／Cursor）を指定してください。以降は同じブラウザで設定を再利用し、各章の元ファイルを開けます。リンクが使えない編集ソフトでは「編集ファイルのパスをコピー」から「ファイルを開く」へ貼り付けます。ブラウザの原稿本文は生成時点の閲覧用コピーであり、ダウンロードしたコピーの編集だけでは正本へ保存されません。

原稿ページも設計書と同じ管理者・システム担当者限定で配信します。API・DBの自動生成一覧には手編集用Markdownがないため、このリンクは手動編集する全体章・機能章に表示します。

```bash
# MarkdownからHTMLを生成
npm run docs:system-design --prefix backend

# 現行DBの構造だけを取得（実データは取得しない）
npm run docs:system-design:schema --prefix backend

# 生成物と機能網羅性を検査
npm run docs:system-design:check --prefix backend

# backend/src/permissions.js に登録済みの新機能の雛形を作る
npm run docs:system-design:scaffold --prefix backend -- <feature_key>
```

DB変更時は全migrationを適用した検証DBを使ってスキーマを更新します。本番DBを文書生成へ使用しません。

## 機能章の必須項目

`機能/<feature_key>.md` はfrontmatterと次の見出しを維持します。

1. 目的と設計意図
2. 利用場面と操作手順
3. なぜこの手順で利用するか
4. 利用例と完了の確認
5. 作成・変更の経緯と根拠
6. 利用者・権限
7. 前提・入力・処理・出力
8. 関連機能・前後工程
9. 主要API・データ
10. 状態・制御・注意点
11. 現行業務との乖離・確認事項
12. 今後の改善

操作説明は「使う場面 → 操作 → 確認する結果 → 次の業務」の順で記載します。経緯には決定日・Issue・資料の節など追跡できる根拠を添え、記録のない導入理由や会話を推測して事実として書きません。例は架空のものとし、計算例の省略条件も明記します。

初めて使う人は `08_実務での使い方.md` から読み、各機能章の利用手順へ進んでください。2026-09-25に全25機能へ利用手順・理由・確認例・経緯を追記しました。

機能カタログに新しいキーが追加されたのに章がない場合、CIは失敗します。frontmatterの `related_features`、`primary_tables`、`api_prefixes`、`specs` はカンマ区切りで記載します。

## 業務確認の記録

未確認事項を推測で「一致」に変更しません。`04_業務乖離チェック.md` の担当、確認日、対応方針を更新し、業務仕様を変える決定は `仕様MD/05_decision_log.md` にも記録します。
