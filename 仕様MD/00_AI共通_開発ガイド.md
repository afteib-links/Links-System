## 2. ツールの役割（開発可）

| ツール | 主な使い方 | 開発する場合 |
|--------|------------|--------------|
| **PC Cursor** | 機能実装・PR・`.cursor/rules` | 標準。`cursor/<name>-148a` |
| **PC Antigravity** | 仕様整理、レビュー、ドキュメント、**コード実装** | **同じ Git ルール**（ブランチ・PR）。実装前に [`00_現状スナップショット.md`](00_現状スナップショット.md) |
| **Cursor Cloud（モバイル）** | 外出先の小タスク | スコープを小さく、draft PR |

Antigravity でコードを書くときも **Cursor 専用の秘密**（`.env` 値の新規露出など）は避け、変更は必ず Git に残す。

## 3. 作業開始の共通手順

```bash
cd <Links-System>
git fetch origin
git status -sb
./scripts/print-project-status.sh
```

1. [`00_現状スナップショット.md`](00_現状スナップショット.md) を開き、更新日・main・フェーズを確認  
2. 触る機能の仕様・計画を開く  
3. ブランチを決める（§4）  
4. 実装後: ローカル `docker compose up --build -d`、必要なら `/api/health`  
5. PR 作成 → もう一方のツールでレビュー可能

## 4. ブランチ・衝突回避

### 残す長寿命ブランチ

- `main` — 配布正  
- `cursor/all-features-draft-148a` — 通し試験  
- `Antigravity-making` — Antigravity 側の仕様・試験（docs 多め）

### 機能開発

```text
git checkout main && git pull origin main
git checkout -b cursor/<英語短名>-148a
# 実装 …
git push -u origin cursor/<英語短名>-148a
# → PR to main
```

**Antigravity が実装する場合の推奨:**

| パターン | ブランチ | 備考 |
|----------|----------|------|
| Cursor と別機能 | `cursor/<name>-148a` | 命名を揃え、PR は誰が書いても同じ |
| 仕様＋小実装の試験 | `Antigravity-making` | マージ前に Cursor で diff 確認 |
| 大きな機能 | `cursor/<name>-148a` | `main` から切る（Antigravity でも可） |

**禁止に近いこと:**

- Cursor と Antigravity が **同じ feature ブランチを同時編集**（必ず `fetch` して担当を分ける）
- `main` への直接 push（保護ブランチ想定）
- 未合意の `data/mysql` 削除

---

## 5. レビューの回し方（Antigravity ↔ Cursor）

1. Antigravity: PR diff をレビュー → 指摘を [`計画/reviews/`](計画/reviews/) に Markdown で残す（テンプレ: [`計画/reviews/README.md`](計画/reviews/README.md)）  
2. Cursor: 指摘を同 PR または別 PR で反映  
3. 仕様が変わったら **同じ PR で `仕様MD` を更新**
