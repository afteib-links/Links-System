## 2. ツールの役割（開発可）

| ツール | 主な使い方 | 開発する場合 |
|--------|------------|--------------|
| **PC Cursor** | 機能実装・PR・`.cursor/rules` | 標準。`cursor/<name>-148a` |
| **PC Antigravity** | 仕様整理、レビュー、ドキュメント、**コード実装** | **同じ Git ルール**（ブランチ・PR）。実装前に [`00_現状スナップショット.md`](00_現状スナップショット.md) |

Antigravity でコードを書くときも **Cursor 専用の秘密**（`.env` 値の新規露出など）は避け、変更は必ず Git に残す。

## 3. 作業開始の共通手順

```bash
cd <Links-System>
git fetch origin
git status -sb
./scripts/print-project-status.sh
```

1. [`00_現状スナップショット.md`](00_現状スナップショット.md) を開き、更新日・main・フェーズを確認  
2. 触る機能の仕様・計画を開く  
3. ブランチを決める（§4）  
4. 実装後: ローカル `docker compose up --build -d`、必要なら `/api/health`  
5. PR 作成 → もう一方のツールでレビュー可能

## 4. ブランチ・衝突回避

### 残す長寿命ブランチ

- `main` — 配布正  
- `cursor/all-features-draft-148a` — 通し試験  
- `Antigravity-making` — Antigravity 側の仕様・試験（docs 多め）

### 機能開発

```text
git checkout main && git pull origin main
git checkout -b cursor/<英語短名>-148a
# 実装 …
git push -u origin cursor/<英語短名>-148a
# → PR to main
```

**Antigravity が実装する場合の推奨:**

| パターン | ブランチ | 備考 |
|----------|----------|------|
| Cursor と別機能 | `cursor/<name>-148a` | 命名を揃え、PR は誰が書いても同じ |
| 仕様＋小実装の試験 | `Antigravity-making` | マージ前に Cursor で diff 確認 |
| 大きな機能 | `cursor/<name>-148a` | `main` から切る（Antigravity でも可） |

**禁止に近いこと:**

- Cursor と Antigravity が **同じ feature ブランチを同時編集**（必ず `fetch` して担当を分ける）
- `main` への直接 push（保護ブランチ想定）
- 未合意の `data/mysql` 削除

## 9. 開発・コンポーネント設計ルール

### フロントエンド作成ルール（Antigravity / Cursor共通）
- **仕様優先**: 必ず `仕様MD/` 以下に画面仕様書（`個別機能仕様書：*.md`）を作成または参照の上作業を開始する。
- **配置パス**: `frontend/` 配下（例: `frontend/js/`, `frontend/index.html` 等）に配置。
- **共通化と再利用（最重要）**:
  - UIコンポーネントやユーティリティ関数は新規に作らず、既存の共通ライブラリ・共通モジュール（例: 共通ダイアログ、共通テーブル、`shared` 関数など）を優先して再利用・拡張する。
  - テストコードや共通ロジックも標準ライブラリ化し、コードの重複を徹底的に避ける。

## 10. DBマイグレーションルール

### DBマイグレーション管理（Antigravity / Cursor共通）
- **配置パス**: `db/migrations/` （連番付き SQL ファイル: 例 `013_new_feature.sql`）
- **ルール**:
  - 既存のマイグレーション SQL や `data/mysql/` 内の実データを破壊・削除しない。必ず新しい連番 SQL ファイルを追加する。
  - DBスキーマを変更・追加した場合は、連動する `backend/src/routes/` 側のクエリおよび `frontend/` 側の API 呼び出し/データハンドリングの修正を **同コミット/PR で必ず行う**。

## 11. API開発ルール

### API開発（Antigravity / Cursor共通）
- **仕様優先**: `仕様MD/` や API 設計ドキュメントにルーティングとレスポンス構造を整理した上で実装する。
- **配置パス**: `backend/src/routes/` （例: `backend/src/routes/companies.js` 等）
- **共通化と影響範囲の更新**:
  - 認証・認可ミドルウェア（`auth.js` 等）やエラーハンドリング、共通ユーティリティを再利用する。
  - API のレスポンス仕様やエンドポイントを変更した場合は、呼出元である `frontend/` 側の処理もセットで更新する。

## 12. テスト・本番運用・保守メンテナンス規約

### テストおよび動作検証ルール
- **自動・手動テスト**:
  - 新機能追加・修正時は `backend` の API テストおよび主要な UI 動作テストを実施・更新する。
  - 既存共通ライブラリ（ヘルパー・ユーティリティ・コンポーネント）に対する破壊的変更がないか動作検証を行う。
- **ローカル検証**: `docker compose up --build -d` を起動し、`/api/health` および影響画面の回帰確認を実施。

### 本番運用（NAS）およびメンテナンス運用方針
- **NAS（ASUSTOR / QNAP）同期手順**:
  - 本番・テスト NAS への反映は、必ず `main` にマージされたコミットを対象とし、`scripts/nas-sync.sh --backup` を用いてバックアップを取りながら実施する。
  - DB マイグレーション適用時は、コンテナ起動時の自動適用ログ（`schema_migrations`）を確認し、正常適用を検証する。
- **障害対応と修正ルール**:
  - 本番障害やバグ修正を行う際は、直ちに緊急修復用ブランチ（`cursor/hotfix-<issue>-148a` または `antigravity/hotfix-<issue>`）を `main` から作成して対応する。
  - 原因追求と修正内容は必ず `仕様MD/05_decision_log.md` または `計画/reviews/` に記録を残す。
