# 業務仕様確定と再設計準備

> **状態**: 着手前の共通ロードマップ
> **目的**: 日報・前払・分割返済・請求・支払・帳票・入出金管理を、複数AIで競合なく本実装へ進めるための順序を定める。

## 前提

- 現在のコードとHTMLプロトタイプは仮組・再利用候補であり、業務仕様の正本ではない。
- `09_日報・精算・帳票_業務要件.md` と `10_入出金管理・FB_業務要件.md` を、今後の設計判断の入口とする。
- 作業中の情報はGitHub IssueとDraft PRに残す。共有の作業ロックファイルは作らない。

## フェーズ

### Phase 0: 運用の土台（完了）

- 全AI共通の `AGENTS.md`、Cursor/Antigravityの補助入口、Issue/PRテンプレート、最小CIを用意する。
- 現在地を `00_現状スナップショット.md` に更新する。

### Phase 1: 業務事実の確定

次の未確定事項を、実Excel・帳票・実務説明から確認して決定ログへ記録する。

1. 日報の全項目・入力単位・承認状態・計算根拠（D-01）
2. 請求・支払の締め、集約、手修正、確定後訂正（D-02、D-05）
3. 控除・税・端数・保険・会費・前払手数料（D-03、D-04、D-06）
4. 分割返済の契約・利子・残高・控除不能時（D-07）
5. 月6回の管理回、休日、FB、実入出金（F-01〜F-06）

このフェーズでは、金額計算やDBの本実装を開始しない。

### Phase 2: 既存資産の監査

Links-Systemと、必要に応じて旧BMSを読み取り専用で調査し、各機能・テーブル・Excel取込・帳票を次の3区分にする。

- そのまま再利用できる
- 修正して再利用できる
- 作り直す

監査結果は、対象資産・根拠・影響範囲・判断保留をIssueまたは `仕様MD/計画/reviews/` に残す。旧BMSを新しい業務仕様の正本にしない。

### Phase 3: 本設計

Phase 1・2の結果から、以下を順に設計し、レビューしてから実装Issueへ分割する。

1. 用語・エンティティ（前払と分割返済、管理回・予定・実績を分離）
2. MariaDBスキーマと既存データへの移行方針
3. 計算明細・調整・スナップショット・訂正の状態遷移
4. API契約、権限、画面、PDF帳票テンプレート
5. Excel取込と匿名化済みテストデータ

### Phase 4: 検証可能な縦切り実装

小さな機能単位で、`DB migration → API → 画面 → テスト → PDFプレビュー` を1PRにまとめる。優先順は、日報実績、計算明細、前払、支払控除、請求、入出金管理、FBとする。

## 並行してよい作業

| 作業 | 担当範囲 | 同時編集してはいけない対象 |
|---|---|---|
| 日報項目の業務ヒアリング整理 | `09`のD-01だけ | 日報DB・計算サービス |
| 控除・前払・分割返済の確認 | `09`のD-03/D-06/D-07だけ | 支払計算・migration |
| 入出金・FBの確認 | `10`のF-01〜F-06だけ | 入出金DB・FB出力 |
| 既存コード資産監査 | 読み取り専用のレビュー記録 | 実装ファイル |
| 最小CI・開発運用の改善 | `.github/`・`docs/development/` | 業務仕様・本実装 |

同じ仕様MDを複数人が更新する必要がある場合は、章を担当別に分けるか、先に1つのDraft PRを完了させる。

## 最初のIssue候補

1. `日報の入力項目と計算項目をExcelから棚卸しする`
2. `前払の対象・単価・手数料・取消ルールを確定する`
3. `分割返済の契約と返済計画を確定する`
4. `請求書・支払書の帳票種類と確定後の訂正を確定する`
5. `月6回の入出金管理回とFB運用を確定する`
6. `Links-System/旧BMSの再利用資産を読み取り専用で監査する`

各Issueは [`docs/development/AI_WORK_REQUEST_TEMPLATE.md`](../../docs/development/AI_WORK_REQUEST_TEMPLATE.md) の項目を満たしてから実装に着手する。
