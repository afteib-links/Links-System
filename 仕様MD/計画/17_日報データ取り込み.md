# 日報データ取り込み機能 実装計画

> **状態**: Phase 1をDraft PR #59で検証中
> **作成日**: 2026-09-04
> **対象**: 日報入力画面、取込管理、原本・添付保管、Excel／メール／FAX解析
> **前提**: 初期版は利用者がファイルをアップロードし、解析結果を確認・修正してから日報へ反映する。外部サービスの受信箱へ直接接続する機能は後続段階とする。

## 1. 目的

事務担当者がメール、FAX、Excelで受領した日報情報を、日報入力画面へ安全かつ効率的に取り込めるようにする。

取り込んだ値は直接確定せず、原本と解析結果を対応付けた「取込確認待ち」として保持する。利用者が案件、勤務日、勤務時間、距離、経費等を確認した後、既存の日報計算エンジンで再計算して下書き日報へ反映する。

```text
ファイル選択
  → 原本保存・重複確認
  → 形式別解析
  → 案件／パートナー候補照合
  → 取込プレビューで確認・修正
  → 入力値検証
  → 下書き日報へ反映
  → 日次確認・月次承認（既存フロー）
```

## 2. 現状と設計方針

### 2.1 現状

- `daily_reports` には `input_source_type` と `scanned_image_url` があるが、原本アップロード、解析、確認キュー、複数ファイル、重複防止は未実装である。
- 日報画面は案件×対象月のグリッドで、登録時に既存計算エンジンを通して請求額・支払額を計算している。
- 日報仕様では入力元を画面、FAX、Excel取込、OCR、Web、メール、その他に分け、初回入力元を後の修正で上書きしないことが確定している。
- 原本・添付はNASへ保存し、管理者・事務員・承認担当者だけが閲覧できる。初期保存期間は3年で、通常バックアップ対象外とすることが確定している。

### 2.2 共通方針

- 全形式を同じ「取込バッチ → 取込行 → 日報反映」の仕組みに集約し、形式固有処理は解析アダプターとして分離する。
- 外部ファイル内の計算金額は参考値として保持できるが、日報へ反映する請求額・支払額は既存計算エンジンで再計算する。
- 原本、解析値、利用者による修正値、最終反映値を分離し、誰がいつ何を変更したか追跡できるようにする。
- 解析の信頼度にかかわらず自動確定は行わない。確認済みの行だけを下書きまたは差戻し状態の日報へ反映する。
- 既存の確認済み、月次承認待ち、承認済み、請求・支払処理済み日報は取込処理で上書きしない。

## 3. 対象範囲

### 3.1 初期版に含めるもの

#### Excel

- `.xlsx` と `.csv` を受け付ける。旧形式 `.xls` は初期版では受け付けず、`.xlsx` への変換を案内する。
- シート、見出し行、データ開始行を選択し、列と日報項目を画面上で対応付ける。
- 列対応を名前付きテンプレートとして保存し、同じ送信元・同じ帳票形式で再利用する。
- 1ファイルに複数案件・複数日・同日複数作業行が含まれる場合も、1行ずつ確認・反映できるようにする。
- セル結合、日付シリアル値、全角文字、`8.00`等の時刻表記を正規化する。数式・外部参照は初期版の解析対象とせず、値へ変換したファイルの再提出を案内する。

#### メール

- `.eml` ファイル、メール本文を保存したテキスト、およびメール添付ファイルのアップロードを受け付ける。
- 件名、送信元、受信日時、本文を原本メタデータとして保存する。
- Excel／CSV添付はExcel解析へ、画像／PDF添付はFAX・画像解析へ渡す。
- 本文からの抽出は、送信元ごとの項目名・行形式を定義したマッピングテンプレートを使用する。HTMLメールはスクリプトと外部読込を除去して表示する。
- Gmail、Microsoft 365等の受信箱へ直接接続する機能は初期版に含めない。

#### FAX・画像・PDF

- PDF、PNG、JPEG、WebP、TIFFを受け付け、原本を日報と紐付けて保存する。
- 左側に原本プレビュー、右側に解析候補・日報入力項目を表示し、ページを見比べながら修正できるようにする。
- OCRは日本語対応のローカル処理を候補抽出に使用する。活字と定型帳票を優先し、手書き値は信頼度が低い前提で要確認にする。
- OCR結果は自動登録せず、項目ごとの信頼度と原文位置を表示する。日付、時刻、金額等の業務検証に通らない値はエラーとする。
- OCRエンジンが利用できない環境でも、原本を見ながら手入力して同じ取込確認フローを完了できるようにする。

### 3.2 後続段階

- Gmail／Microsoft 365等の専用メールボックス監視。
- NAS上のFAX受信フォルダ監視、または利用中のインターネットFAX API連携。
- 送信元、件名、ファイル名等による自動取込テンプレート選択。
- 高精度な外部OCRサービスの比較・導入。個人情報・保存地域・費用を確認して別途決定する。
- 条件が確実に一致するデータの自動日報登録。十分な運用実績と誤登録率の測定後に別Issueで判断する。

### 3.3 対象外

- 取込時の自動承認、月次承認の省略、請求・支払の自動確定。
- メール送信、FAX送信、受信メールの削除・移動。
- Excelのマクロ実行、外部リンク更新、埋め込みオブジェクトの実行。
- 原本ファイルをGitリポジトリやMariaDBのBLOB列へ保存すること。

## 4. 画面と操作

### 4.1 日報入力画面

- 上部の主要操作に「データ取り込み」を追加する。
- 押下後に取込ダイアログを開き、入力元を「Excel」「メール」「FAX／画像」から選択してファイルを指定する。
- アップロード完了後は取込確認画面へ移動し、日報入力画面へ戻っても未完了バッチを再開できるようにする。
- 日報行には入力元アイコンと原本表示ボタンを追加する。入力元は初回反映後に変更不可とする。

### 4.2 取込確認画面

- 上部にファイル名、入力元、取込者、取込日時、解析状態、対象行数、エラー数、重複候補数を表示する。
- Excelは原文行と変換後の値を表形式で並べる。FAX・メールは原本プレビューと入力フォームを2ペイン表示する。
- 各行に「取込対象」「案件」「パートナー」「勤務日」「開始」「終了」「休憩」「欠勤／研修」「距離」「通行料」「駐車料」「交通費」「行コメント」を表示する。
- 案件候補は案件No、パートナーNo、会社名、対象期間を使って照合し、候補理由を表示する。複数候補または候補なしは利用者の選択を必須とする。
- エラー、警告、重複候補を色だけでなくアイコンと日本語で表示する。
- 「有効行をすべて反映」と行単位の反映を用意する。エラー行は反映できず、警告行は利用者が確認チェックを付ければ反映できる。
- 反映結果から作成・更新された日報行へ移動できるようにする。

### 4.3 取込履歴

- 日報入力画面から、対象案件・対象月に関係する取込履歴を表示する。
- 状態は「アップロード済み」「解析中」「確認待ち」「一部反映」「反映済み」「エラー」「取消」とする。
- 取込取消は未反映データだけに許可し、反映済み日報は既存の日報訂正フローで処理する。
- 同一ファイルを再アップロードした場合は重複警告を表示し、過去バッチを開くか、理由付きで別バッチとして続行する。

## 5. データ設計

既存マイグレーションは変更せず、新しい連番マイグレーションを追加する。現状の次番号は `021` を使用する。

### 5.1 `daily_report_import_batches`

取込操作全体を表す。

- `daily_report_import_batch_id`
- `source_type`: `excel` / `email` / `fax`
- `status`: `uploaded` / `parsing` / `needs_review` / `partial` / `applied` / `failed` / `cancelled`
- `mapping_template_id`
- `source_sender`, `source_subject`, `source_received_at`
- `parser_name`, `parser_version`
- `row_count`, `valid_count`, `warning_count`, `error_count`, `applied_count`
- `created_by_user_id`, `created_at`, `parsed_at`, `completed_at`
- `error_summary`, `extra_data`

### 5.2 `daily_report_import_files`

原本と添付ファイルを表す。1バッチに複数ファイルを許可する。

- `daily_report_import_file_id`, `daily_report_import_batch_id`
- `parent_file_id`: メール添付等の親子関係
- `original_filename`, `stored_filename`, `storage_path`
- `mime_type`, `file_size`, `sha256`
- `page_count`, `preview_path`
- `retention_until`, `deleted_at`, `deleted_by_user_id`, `deletion_reason`
- `replaced_by_file_id`, `is_active`, `created_at`

### 5.3 `daily_report_import_rows`

ファイル中の1行または1帳票上の1作業行を表す。

- `daily_report_import_row_id`, `daily_report_import_batch_id`, `source_file_id`
- `source_sheet`, `source_page`, `source_row_number`, `source_locator`
- `status`: `pending` / `warning` / `error` / `ready` / `applied` / `skipped`
- `raw_data`: 原文から得た値
- `parsed_data`: 解析・正規化した候補値
- `reviewed_data`: 利用者が確定した反映値
- `confidence_data`, `validation_errors`, `validation_warnings`
- `matched_project_id`, `matched_partner_id`, `match_reason`
- `row_fingerprint`, `daily_report_id`
- `reviewed_by_user_id`, `reviewed_at`, `applied_by_user_id`, `applied_at`
- `version`, `extra_data`

### 5.4 `daily_report_import_mappings`

送信元・帳票形式ごとの再利用可能な列／項目対応を表す。

- `daily_report_import_mapping_id`, `mapping_name`, `source_type`
- `sender_pattern`, `subject_pattern`, `filename_pattern`, `sheet_pattern`
- `header_row`, `data_start_row`, `mapping_json`, `normalization_json`
- `is_active`, `created_by_user_id`, `created_at`, `updated_at`, `version`

### 5.5 既存日報との関係

- `daily_reports.input_source_type` は初回反映時に `excel`、`email`、`fax` のいずれかを設定し、通常更新APIからの変更を禁止する。
- `scanned_image_url` は後方互換参照として残すが、新規処理の正本は取込ファイルテーブルとする。
- 取込行の `daily_report_id` により原本、解析値、反映先を追跡する。
- 取込後の手修正は既存監査ログへ `import_correction` として変更前後、修正者、日時を記録する。

## 6. API・バックエンド

### 6.1 API

- `POST /api/daily-report-imports`: multipartで原本をアップロードし、バッチを作成する。
- `GET /api/daily-report-imports`: 対象月、案件、入力元、状態で履歴を検索する。
- `GET /api/daily-report-imports/:id`: バッチ、ファイル、取込行、集計を取得する。
- `POST /api/daily-report-imports/:id/parse`: 解析または再解析を実行する。
- `PUT /api/daily-report-imports/:id/rows/:rowId`: 案件選択や解析値の修正、取込対象外指定を保存する。
- `POST /api/daily-report-imports/:id/validate`: 全行を既存の日報入力規則で再検証する。
- `POST /api/daily-report-imports/:id/apply`: 選択した有効行をトランザクション内で日報へ反映する。
- `GET /api/daily-report-imports/files/:fileId`: 権限確認後に原本またはプレビューを表示・ダウンロードする。
- `POST /api/daily-report-imports/:id/cancel`: 未反映バッチを理由付きで取消す。
- `GET/POST/PUT /api/daily-report-import-mappings`: マッピングテンプレートを参照・登録・更新する。

### 6.2 解析と正規化

- ファイル種別は拡張子だけでなくMIMEタイプとファイルシグネチャで検証する。
- ファイル名は表示用としてのみ保持し、保存名はランダムIDで生成してパストラバーサルを防ぐ。
- Excel解析、メール解析、画像前処理、OCRを独立サービスに分け、共通の日報候補データへ変換する。
- 日付は `YYYY-MM-DD`、時刻は勤務日基準の `HH:MM`（最大`47:59`）、休憩は分、距離は整数km、金額は整数円へ正規化する。
- 全角数字・記号、和暦候補、Excel日付シリアル値、日付をまたぐ終了時刻を正規化し、推測を伴う変換は警告として残す。
- 案件の対象期間外、パートナー不一致、終了が開始以前、休憩超過、対象月不一致等を検証する。

### 6.3 日報反映

- 反映対象の `reviewed_data` から利用者入力可能項目だけを受け取り、計算結果・適用PriceSet等のシステム項目は受け取らない。
- 既存の `applyDailyPriceCalc` を必ず使用し、画面入力と同じ計算・丸め・休日判定を適用する。
- 新規日報は `draft` で作成する。差戻し日報への更新は、対象行を利用者が明示選択した場合だけ許可する。
- 確認済み・承認済み・精算予約済みの日報との競合は行単位エラーにし、他の有効行だけを反映できるようにする。
- 同日複数作業行を許可するため、案件＋勤務日だけでは重複扱いにしない。ファイルハッシュ、取込バッチ、原文位置、正規化値から作る行指紋で同一取込を判定する。
- 同じ取込行の再送は冪等にし、二重日報を作成しない。

## 7. 原本保存・セキュリティ・権限

- 原本は既存の `./data/uploads` ボリューム配下の専用領域へ保存し、リポジトリ管理対象外とする。保存先は環境変数で変更可能にする。
- 1ファイル50MB、1バッチ20ファイル、展開後200MBを初期上限とし、管理設定で上限を小さくできるようにする。
- 許可形式以外、暗号化PDF、パスワード付きExcel、マクロ付きファイル、破損ファイルは解析せずエラー表示する。
- Officeマクロ、埋め込みスクリプト、HTMLメール内スクリプト、外部画像・外部リンクは実行しない。
- 管理者、事務員、承認担当者は原本閲覧可、日報入力権限を持つ管理者・事務員はアップロード・修正・反映可とする。パートナー、企業、営業は原本閲覧と取込操作を不可とする。
- ファイルの表示・ダウンロードを含む全操作を監査ログへ記録する。
- 保存期限は登録日から3年を初期値とし、月末削除候補一覧で管理者または事務員が確認してから本体を削除する。メタデータと監査履歴は残す。
- 原本が通常バックアップ対象外であり、削除後に復元できないことをアップロード画面、設定画面、削除確認画面に表示する。

## 8. 実装段階

### Phase 0: 仕様確定と作業分離

- 本計画の初期版前提を `09_日報・精算・帳票_業務要件.md` と `05_decision_log.md` に反映する。
- 1 Issue＝1ブランチ＝1 Draft PRの原則に従い、現在進行中のUI刷新とは別Issue・別ブランチにする。
- 匿名化したExcel、メール、FAXを各2～3種類準備し、実ファイルはリポジトリへ追加しない。テスト用には構造だけ再現した匿名最小データを作る。

### Phase 1: 共通取込基盤とExcel

- GitHub Issue #58、ブランチ `cursor/daily-report-import-148a`、Draft PR #59で実装・検証する。
- DB、ファイル保存、取込バッチ／行API、履歴画面、権限制御を実装する。
- Excel／CSV解析、列マッピング、プレビュー、検証、日報反映を実装する。
- 既存日報APIで初回入力元が上書きされないようにする。

### Phase 2: メール・FAX・OCR

- `.eml`、本文、添付ファイルの解析を追加する。
- PDF・画像・TIFFのプレビュー生成とローカルOCR候補抽出を追加する。
- 日報画面に原本との2ペイン確認UIを追加する。

### Phase 3: 保管運用と品質改善

- 保存期限設定、月末削除候補、確認削除、メタデータ保持を実装する。
- 実運用の誤認識・修正率を記録し、マッピングテンプレートとOCR前処理を改善する。

### Phase 4: 外部受信連携

- 実際に使用するメール基盤、FAX機器／サービス、NASフォルダ構成を確定する。
- 読み取り専用の受信接続、取得位置管理、重複防止、再試行、接続障害通知を追加する。
- 外部接続ごとに認証情報を環境変数または秘密情報管理へ置き、DB・ログ・Gitへ保存しない。

## 9. テスト計画

### 9.1 単体・API

- `.xlsx`／`.csv`／`.eml`／PDF／画像の正常解析、非対応形式、破損、暗号化、上限超過。
- 全角時刻、Excel日付、24時超え、空欄、複数シート、結合セル、数式エラーの正規化。
- 案件1件一致、候補複数、候補なし、対象期間外、パートナー不一致。
- 同一ファイル再取込、同一行再反映、同日別作業、部分成功、再解析。
- 入力元の不変性、原本リンク、監査ログ、楽観ロック、反映トランザクション。
- 取込値から既存計算エンジンを通した結果が画面手入力と一致すること。

### 9.2 権限・セキュリティ

- 管理者・事務員の取込操作、承認担当者の閲覧、その他権限の拒否。
- 推測したファイルID、パストラバーサル、偽装拡張子、HTMLスクリプト、巨大展開ファイルの拒否。
- パートナー・企業ユーザーが原本URLへ直接アクセスしても取得できないこと。

### 9.3 画面E2E

- Excelアップロード → マッピング → エラー修正 → 一部反映 → 日報行表示。
- FAX原本プレビュー → OCR候補修正 → 日報反映 → 原本再表示。
- メール添付の形式別振り分けと本文解析。
- 重複警告、未完了バッチ再開、取消、反映済み日報への移動。
- 1920×1080、1366×768、390×844で、2ペイン、表内横スクロール、主要ボタンを確認する。

### 9.4 運用確認

- Docker再起動後も原本と取込履歴が残ること。
- `/api/health`、既存日報テスト、請求・支払回帰テストが成功すること。
- Asustorテスト環境でOCR時のCPU・メモリ・処理時間を測定し、負荷が高い場合も非同期処理と手入力フォールバックで操作継続できること。
- 月末削除候補、見送り、削除、メタデータ保持、削除後取得不可を確認する。

## 10. 完了条件

- Excel、メール、FAXの各データを共通取込画面から登録し、原本を保持したまま確認・修正して下書き日報へ反映できる。
- 誤解析、案件未一致、重複、承認済みデータ競合が自動確定されず、利用者に日本語で理由が表示される。
- 取込前後の値、原本、入力元、取込者、修正者、反映先日報を追跡できる。
- 画面入力と取込入力で同じ日報計算結果になる。
- 権限外ユーザーが原本・解析結果へアクセスできない。
- 仕様MD、決定ログ、APIテスト、画面E2E、Docker、health確認、NAS運用注意事項が同一PRで更新される。

## 11. 採用する初期前提

- 初期版は手動アップロード方式とし、メール／FAXの自動受信接続は後続とする。
- 日報反映前に利用者の確認を必須とし、完全自動登録は行わない。
- Excelは `.xlsx` と `.csv`、メールは `.eml` と添付、FAXはPDF・主要画像形式を対象とする。
- FAXのOCRは入力補助であり、手書き内容の正確性を保証しない。
- 原本保存期間は既存決定どおり3年、通常バックアップ対象外とする。
- 計算金額は外部データを正とせず、既存の日報計算エンジンを正とする。
