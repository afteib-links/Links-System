# 請求・支払の運用受入と正式FB準備

> 対象: Issue #52 / `cursor/settlement-uat-148a`<br>
> 実施日: 2026-09-03

## 1. 目的

PR #51で統合した請求・支払・前払・入出金管理について、匿名データを使った業務フロー、権限、PDF、検証データリセットを自動検証する。正式FB、承認分離、銀行明細照合は、下記の未決事項を確定後に別Issueで実装する。

## 2. 今回の受入範囲

- 管理者、総務、経営者、営業、企業、パートナーの一覧・詳細・帳票・PDF権限
- 月次承認スナップショットからの下書き生成と同一日報の二重予約拒否
- 請求先税率の優先、案件集約表示、理由付き負額調整
- 前払・共通控除・個別控除、0円振込、未控除繰越
- 未実行取消による日報予約・前払配賦・繰越残高の復元
- 実行済み支払の直接取消拒否、訂正下書き、新番号PDF、負差額の逆方向予定
- 旧請求・支払`/close` APIの410応答
- 請求書、請求取纏書、支払明細書、給与明細書のA4 PDF
- 空DBへの匿名データ投入、非検証データがあるDBでの検証データ限定リセット

## 3. 検証結果

- バックエンド単体テスト: 43件成功
- Docker: `linkssystem` 1組で再ビルドし、`/api/health` の `db: up` を確認
- 隔離UAT DB: マイグレーション全件、匿名データ4,172日報、請求2件、支払2件、帳票7件を生成
- 権限E2E: 6ロールの許可・拒否とPDFダウンロードを確認
- 精算E2E: スナップショット、予約、税、0円振込、取消、実行後差額訂正を確認
- リセットE2E: `seed_key`なしの既存企業を保持し、匿名データだけを削除・再投入できることを確認
- PDF: 4種すべてA4。複数ページの表見出し反復、余白、文字切れ、敬称を画像で確認

## 4. 受入中に修正した問題

- 営業・パートナーに支払参照機能が付与されず、APIへ到達できない問題
- 精算共通アクセス判定が、請求・支払それぞれに存在しない相手先列を参照して500になる問題
- 支払先の敬称が企業向けと同じ「御中」になる問題
- 複数ページPDFで表見出しと行の改ページ制御が不足していた問題
- 匿名データ限定リセットで、関連精算・前払配賦・案件設定・個別控除ルールの削除順が不足していた問題
- 給与明細書の匿名検証シナリオがなかった問題

## 5. 次段階で決定する事項

### 正式FB（F-04）

- 最初に接続する銀行名とサービス名
- 全銀協形式か銀行固有形式か、総合振込・給与振込の対象範囲
- 文字コード、レコード長、改行、ファイル名、依頼人コード、振込指定日の規則
- 支店番号・口座種別・口座番号・口座名義カナの入力検証
- 出力前チェック、再出力、取消、重複送信防止、銀行取込エラー時の戻し方

### 承認分離

- 作成者と承認者を分ける対象（精算確定、CSV/FB出力、実績登録）
- 金額閾値、代理承認、差戻し、緊急時の例外権限
- 管理回単位または明細単位の承認と、監査ログの保存期間

### 銀行明細照合（F-05）

- 取込対象ファイル/API、対象口座、取込頻度
- 照合キー（予定日、金額、名義、依頼人番号等）と自動一致の許容範囲
- 部分入金、合算入金、手数料差引、過不足、保留、取消の状態遷移
- 手動照合・解除権限と証跡、再取込時の重複防止

## 6. 推奨実装順

1. 対象銀行の仕様書を入手し、正式FBの決定事項を確定する。
2. 口座情報検証と全銀協または銀行固有FB出力を、現行CSVバッチの追加形式として実装する。
3. 運用実績を基に作成者／承認者の分離を追加する。
4. 銀行明細取込と自動照合を追加し、差額・保留運用を確定する。

正式FBを実装するまでは、現行CSVを銀行登録前の確認・転記用として使用し、銀行へ直接送信する正本にはしない。
