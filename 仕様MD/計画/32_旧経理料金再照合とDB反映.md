# 旧経理料金の再照合とDB反映

作業ID: Issue #172。担当: Codex。ブランチ: `codex/accounting-rate-recheck`。

## 合意した変更（2026-09-25）

- 分析表を原本と再照合し、現行DBの料金カード、企業の基本案件、個別案件へ登録する。
- 元パス・シート名・取込先名称に「解除」（「●解除」「〇解除」等を含む）がある移行データを除外する。既取込データと、そのみに属するマスターはバックアップ後に論理削除する。同一パートナーの有効案件・取引は残す。
- 企業の基本料金には、適用年月が最も古い案件料金を一式採用する。同月は元ファイル名、元シート順で決め、異なる案件の単価を混ぜない。選択根拠を保存する。
- 個別案件の料金変更は適用期間付き改定版として保持する。企業基本料金は基本案件、個別料金は個別案件に独立保存する。
- 表示用の `extra_data.fee_items`（行形式）と計算・互換用の `price_set_lines` を同時生成する。

## 再照合

- 実際の売上・支払欄の単価×数量の式から単価セルを特定する。締日説明や補助表を重複採用しない。
- 意味付けはローカルOllama `qwen3.5:4b`。金額・数量・合計・参照セル・DB関連付けは決定的な処理で検証する。
- 支払数量が売上数量を参照する場合は、その参照を組合せの根拠とする。項目順だけで異なる料金を組み合わせない。
- 原本にない金額を推定しない。片側空欄と明示ゼロを区別し、未確定項目・契約条件は料金備考と再照合結果へ残す。
- 同一案件・同一月の異なる料金一式は競合として記録する。

## 反映・復旧

- DB全体ダンプとハッシュ、変更対象ID・変更前データ、登録計画を保存する。個人情報・原本・ダンプはGitに入れない。
- 現行スキーマと既存料金検証／展開サービスを使用する。
- ドライラン、件数・参照検証、実計算エンジンの代表条件検証後、トランザクションで反映する。再実行は登録キーで識別する。
- 解除対象外の承認済み・請求済み・支払済みデータの金額を再計算しない。
- 復旧には反映直前のダンプを使用する。論理削除データはDBに保持する。

## 完了条件

- 解除対象が通常一覧に表示されない。
- 基本案件と個別案件から料金カード・金額・適用期間が確認できる。
- 実計算エンジンが対応する料金と計算条件を選択する。
- 未対応条件と料金を作れなかった対象を具体的に報告する。

## 実装・反映結果（2026-09-26）

- 解除を除外した1,542シートを原本のセルと数式で再抽出。Ollama `qwen3.5:4b` の202ラベル分類と計算パターン評価を保存した。モデルの説明には単価/数量の取り違え等もあり、説明を無検証で計算条件には採用しない。
- `PRODUCT(単価,数量)`、中間列が空欄の `PRODUCT(単価:数量)`、単純積、積の `ROUNDDOWN/ROUNDUP/ROUND`、分単位の `ROUNDUP(単価/60*数量,0)` を識別。請求/支払5,503組を作成した。
- 企業基本107件、個別174案件・243改定版を現行DBへ登録。料金カードと互換行を同時生成し、基本案件/個別案件の選択料金も更新した。
- 解除に関わる企業3、パートナー205、基本案件3、個別案件205、日報7,209、請求319、支払645と従属明細を論理削除。旧仮料金36件（解除11、再照合版へ置換25）も論理削除した。
- DB全体約20MBのダンプを取得。金額を含む日報・請求・請求明細・支払・支払明細の全行について、削除フラグ/版番号/更新日時を除いたSHA-256が前後一致した。
- 基本計算登録済194料金版、要確認156料金版。要確認でも単価と証跡は表示するが、日報自動計算は422 `legacy_rate_review_required` で止める。0円計算で既存値を上書きしない。
- 画面の「原本照合・計算ロジック」に元ファイル/シート、請求/支払の単価、数量式、合計式、検算差額、別資料、確認事項を表示する。通常編集でも証跡を保持する。
- 25案件には料金を生成していない。うち24件は以前の移行で請求書名がパートナー名となった疑いのある記録、1件は日報から料金を得られない記録。解除とは異なるため追加削除はしていない。
- 要確認の主因: 請求/支払の対応不明、距離条件、基準時間、同月の別作業、派遣の月合計分と深夜加算、商品個数。20分閾値/30分刻みも現行丸めには直結しない。元の月次合計と日次丸めの同等性は、単価照合だけでは保証しない。

## 運用・復旧

- スクリプトは `legacy_rate_recheck.py` → `legacy_rate_logic_review.py` → `legacy_rate_plan.py` → `legacy_rate_apply.js`。適用は既定でロールバックする。確定時は全体バックアップのSHA-256一致と取得時DBスナップショット一致が必須。
- 全350件の登録キーが存在する再実行は `already_applied` として変更しない。一部だけ存在する場合は停止する。
- 個人情報を含む原本・証跡・計画・ダンプは除外済の `tmp/` と `backups/` のみに置く。実行結果は同作業の非公開 `tmp/accounting-rate-recheck/` に保存。
- DB復旧は対象DBを停止/保守状態として反映直前のダンプを復元する。後続の入力がある場合は全体復元せず、退避と差分復旧を計画する。元Excelは変更していない。
- 稼働アプリは既存コンテナの対象ファイル一致を確認後、バックアップ・限定反映・再起動した。他作業の環境を巻き戻さないためCompose全体再ビルドは行っていない。永続的な次回ビルドには本変更を含むブランチ/マージ済コミットを使用する。
- 検証: Python6件、関連Node22件、実DB基本計算544件、要確認拒否105件、UI/APIの現行281件・代表詳細3件、ブラウザ例外0、`/api/health` DB up。
- 追加検証: 証跡UIのエスケープ/空欄区別/保存時保持3件、共通一覧カタログ8件を通過。コンテナ全体テストは262件中、初回255通過・7失敗。うち1件は追加列のカタログ漏れで修正・再実行通過。残り6件はコンテナにDocker運用ファイルが含まれないことが原因で、該当テストをローカルの完全な作業ツリーで再実行し10件通過。
