# 仮組先行の進め方（全体ルール）

> 状態: **適用中**  
> これから作る機能は、すべてこのルールに従う。

## 方針

いきなり「完成形の本作成」にせず、次の順で進める。

```mermaid
flowchart LR
  Spec["仕様MD参照"] --> Draft["仮組"]
  Draft -->|"動かして確認"| Review["全体確認と見直し"]
  Review --> Final["本作成"]
  Final --> SpecUpdate["仕様MD更新"]
```

1. **仮組** … その機能に必要なものを一式作る（DB・画面・操作できる状態）。実際に動かして問題がないことを確認する
2. **見直し** … DB構成・画面構成・連携キーを再検討し、最適な形に直す方針を固める
3. **本作成** … 見直し結果を反映し、完成度を上げた本番向け実装にする

## 仮組の定義

### 含めるもの（必須）

- **機能は一式**: 対象機能の仕様にある画面・操作を仮組として一通り作る（「枠だけ・ボタンだけ」で終わらない）
- **DBも作る**: テーブル・項目・主キー／外部キー（連携キー）を実装する。項目洗い出しと連携確認が目的
- **画面も作る**: 一覧・詳細など仕様どおりの画面切替・入力・保存・削除などが実際に動く
- **実稼働確認**: ローカル（または同等環境）で動かして、一連の操作に問題がないことを確認する
- 既存基盤（ログイン・権限・MariaDB）に載せる

### 仮組での作り方の温度感

- **画面デザイン**: 大枠でよい（レイアウト・遷移・項目の有無が分かればよい）
- **重要部分**: 業務上クリティカルな箇所（必須項目、1対多、連携キー、論理削除など）は詳細に作ってよい
- 見た目の作り込み・細部のUI調整は本作成側に寄せる

### 仮組でやりすぎないもの

- 見た目の最終調整（余白・装飾・文言の磨き込み）
- 見直し後に変わる前提の過剰な最適化
- 帳票PDFなど、対象機能のコア確認に必須でない完成度の高い周辺機能

## 見直しの定義

仮組を動かしたあと、次を確認・修正方針化する。

- DB項目の過不足、型、区分マスタ
- テーブル間の連携キー（FK）が実務・後続機能と合うか
- 画面構成（一覧項目、詳細セクション、動的行の持ち方）
- 権限・操作導線

問題がなければ本作成へ。差があれば仕様MDと計画を更新してから本作成する。

## 本作成の定義

- 見直しで固めた DB・画面構成に合わせて実装を整える
- バリデーション、楽観ロック、権限、エラー表示などを本番品質にする
- UIを大枠から実用レベルへ仕上げる
- `Login.md` / 個別機能仕様 / `06_development_environment.md` に整合させる
- 仮組〜見直しの決定を仕様MDに反映する

## 計画への記録

- 各機能の計画書には「仮組 / 見直し / 本作成」の段階と状態を書く
- 新しい計画は必ず `仕様MD/計画/` に追加する
