# 本番移行ツール

## 1. 目的

Windowsのローカル作業ツリーにあるLinks-Systemを、ローカルMariaDBの内容または本番の既存データを選択してQNAP本番環境へ繰り返し反映する。

入口はリポジトリ直下の `本番移行.cmd` とする。実行にはQNAPのSSH接続情報、SSHの公開鍵認証またはパスワード認証、Container Station、本番用 `.env` が必要である。秘密情報とDBダンプはGitへ追加しない。

## 2. 選択項目

| 項目 | `yes` / `update` | `no` / `replace` |
|---|---|---|
| システムバックアップ | 反映前の本番コードと `.env` を `backups/system_*.tgz` に保存 | 保存しない |
| DBバックアップ | 変更前の本番DBを `backups/` に論理バックアップ | 保存しない |
| DB処理 | `update`: 本番データを保持し、起動時マイグレーションだけを適用 | `replace`: 本番DBを削除し、ローカルDBダンプへ完全差し替え |
| ファイル更新 | ローカルの `data/uploads` と `data/pdf` を追加・上書き | 本番ファイルを変更しない |
| 初期秘密値の更新 | DB内部資格情報とセッション秘密鍵が初期値の場合だけ安全なランダム値へ更新 | 秘密値を変更しない |

システム本体は毎回、Git追跡中のファイルとGit除外されていない未追跡ファイルから、実行時のローカル作業ツリーをアーカイブして反映する。このため未コミットのコード変更も含まれる一方、削除済みファイルは含まれない。`.git`、`.env`、`data`、`backups`、`node_modules`、テスト・生成出力、AI用worktreeは転送しない。本番側の `.env`、DB永続データ、既存バックアップはコード更新時にも保持する。ファイル更新を選んだ場合だけ、`data/uploads` と `data/pdf` を別アーカイブで転送する。

## 3. 実行方法

通常は `本番移行.cmd` をダブルクリックし、画面の質問へ回答する。接続名、SSHユーザー、SSHポート、秘密鍵のパス、配置先はGit対象外の `scripts/production-deploy.local.json` へ保存し、次回の既定値にする。秘密鍵そのものとパスワードは保存しない。SSHがパスワード認証の場合は、まとめたファイルの転送時と本番実行時にパスワードを入力する。公開鍵認証を設定するとパスワード入力を省略できる。

引数を固定して実行する場合の例:

```powershell
powershell.exe -NoProfile -File scripts/production-deploy.ps1 `
  -NasHost 192.0.2.10 -SshUser admin `
  -SystemBackup no -DatabaseBackup no `
  -DatabaseMode replace -Files yes -NonInteractive
```

実処理を行わず計画だけ確認する場合は `-DryRun` を追加する。

## 4. DB処理

- `update` は本番DBを削除しない。新しいアプリをビルドして起動し、`schema_migrations` に未適用のSQLだけを適用する。
- `replace` はローカルのappコンテナを一時停止して一貫したSQLダンプを作り、本番DBを再作成して取り込む。全セッションを削除するため、利用者は再ログインする。
- バックアップなしの `replace` は復旧用DBダンプを作らない。選択内容を確認してから実行する。
- ローカルDBに有効な `admin` 管理者が1件あることを必須とする。移行前後で `admin` のパスワードハッシュのSHA-256を照合し、パスワードを再生成・変更しない。不在または不一致の場合は移行成功にしない。
- 初期秘密値の更新は `MYSQL_ROOT_PASSWORD`、`MYSQL_PASSWORD`、`DB_PASSWORD`、`SESSION_SECRET` だけを対象とし、`ADMIN_LOGIN_ID`、`ADMIN_PASSWORD`、usersテーブルは変更しない。

## 5. 成功・停止条件

成功条件は、本番の `http://<QNAP>:8080/api/health` が `db: "up"` を返し、Composeのコンテナ状態を取得できることである。

失敗すると `tmp/production-deploy-failures.txt` の連続失敗回数を増やす。3回連続失敗した後は次回実行を拒否し、原因確認後に `-ResetFailureCount` を明示した場合だけ再開する。成功時は回数を0へ戻す。

本番側の実行履歴は、実行日時、ID、各選択内容、実行理由・メモを含めて `backups/production-deploy.log` に残す。システムバックアップなしでコード反映に失敗した場合でも、`.env`、DB、添付、PDFは削除しない。

転送用の一時ディレクトリは、容量の小さいQNAPの `/tmp` ではなく、Links-System配置先と同じ共有ストレージの親ディレクトリに作成する。成功時にその一時ディレクトリだけを削除する。

QNAPのSSHユーザーHOMEがContainer Stationの書込み不可領域を指す場合に備え、Docker/buildx用のHOMEと設定領域はLinks-System配下の `.production-deploy-home` に固定する。ここにはDockerクライアントの作業設定だけを置き、アプリDBや秘密情報は置かない。

## 6. 初回準備

本番パスは既定で `/share/Container/Links-System` とする。ストレージ名を含むQNAPでは、例として `/share/CACHEDEV1_DATA/Container/Links-System` を `-ProjectPath` へ指定できる。初回実行前に次を満たす。

1. QNAPにContainer Stationを導入し、SSH公開鍵認証を有効にする。
2. `/share/Container/Links-System/.env` に本番専用のDBパスワード、セッション秘密鍵、管理者情報を設定する。
3. 社内LANからQNAPの8080番ポートへ接続できるようにする。

`.env` がない場合、ツールは既定の弱い秘密値で起動せず失敗終了する。
